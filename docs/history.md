# Lumina history

How each phase and feature was built: what was measured, what was decided and why, and what was left open. [PLAN.md](../PLAN.md) holds the current decisions and what is next; this is the record behind them, moved out of PLAN.md in #113. It is not updated as the code changes, so check the code before relying on a detail.

**Phase 0: scaffold.** `pyproject.toml`, `src/lumina/` layout, `CLAUDE.md`, ruff, pytest, CI, layer test, rewrite `README.md`. Resolve the PySide6 source decision. Done.

**Proof of concept (done).** A thin slice through every layer, ahead of Phases 1 and 2: open a folder, scan it on a thread (`core/scanner.py`), a lazy thumbnail grid (`qt_models/photo_model.py`, decoded in worker processes by `core/images.py`, bounded in-memory cache), a viewer with arrow-key stepping (`qt_models/previews.py`, newest request wins), the filehouse theme. RAW goes through `core/raw.py` (embedded preview, LibRaw flip, half-size fallback). No database, no disk cache, no metadata. Known gaps: not yet tried on real CR3 files; thumbnail requests for rows scrolled past are not cancelled. (The `.desktop` file and the app icon came later: `install.sh`.)

**Phase 1: CR3 ingest, no UI.** `raw.py`, `metadata.py`, `thumbs.py`, tests with small sample CR3, JPEG, a RAW with no JPEG preview, and a corrupt file. Proves CR3 handling first. Built, except the check against real CR3 files:

- **RAW samples.** Real CR3s are 20 to 50 MB, so they are not in git: `tests/core/test_samples.py` reads them from the git-ignored `tests/samples/` (or `$LUMINA_SAMPLES`) and skips without them. It checks that the full-size preview is used (not the 160 x 120 one), that it is upright, and that the files are left as they were. Everywhere else, including CI, RAW handling is tested with tiny DNG files the tests write (`tests/rawfiles.py`): JPEG preview, bitmap preview, no preview (half-size decode), turned, cut short. LibRaw reads them through the same paths as CR3.
- **Metadata.** One `exiftool -stay_open` process fed batches through stdin, `-json -n`, only reading. Paths are passed absolute (a name starting with `-` is never an option) and as `#[CSTR]` lines when they have a newline or leading or trailing space. A missing or unreadable file is a `PhotoError` naming it; a file exiftool reads as something else (`FileType` "TXT") or reads past a fault in (`Warning`) is not an error here: telling a bad photo apart is the decoder's job. One warning is kept, though (#10, schema 6, `photos.damage_warning`): a CR3 whose CTMD record exiftool finds cut short ("Truncated CTMD record", "Short CTMD record") was damaged copying from the card in every case seen, while its embedded JPEG, which the grid and the viewer show, stays intact. Such a photo gets a warning badge on its thumbnail's top right corner, says why in its tooltip and in the viewer's status bar, and is still listed as any other (`core/metadata.damage_warning`). Migrating to schema 6 marks the CR3s already read to be read again by the next scan, so damage done before is found. The Develop view checks the raw data itself: a decode in which more than 0.1 % of the raw values are further under the black level than 1/40 of the white level (no exposure makes those; a damaged 90D file had 1 to 38 %) is refused with an error that says the raw data is damaged and names the file (`core/edit/source`), and so is an export of it. Neither check alone catches every damaged file; neither repairs anything. A process that dies is started again; one that hangs is killed after a timeout.
- **Thumbnail cache.** `$XDG_CACHE_HOME/lumina/thumbnails/v1/<id[:2]>/<id>-<side>.webp`, written to a temporary file and renamed, never next to a photo. A damaged file is removed and made again; a cache that cannot be written still gives thumbnails. About 10 KiB a thumbnail at 320 px; a hit is about 1 ms against 18 ms to decode a 1 MB JPEG. The size is limited and pruned (#5, below).
- **CI** runs the tests in a `fedora:44` container with Fedora's exiftool, as an ordinary user, and fails rather than skips a test that needs exiftool (`LUMINA_REQUIRE_EXIFTOOL=1`).

**Phase 2: library.** `db.py`, `scanner.py`, persistent job queue with progress, grid view (`QListView` IconMode, lazy thumbnails), basic filters (date, camera, lens), single-photo viewer. Watch folders, handle unplugged drives.

**Phase 2 as built.**

- **Photo identity.** A volume id and the path from that filesystem's root (`core/volumes.py`, from `/proc/self/mountinfo` and `/dev/disk/by-uuid`). The id is `uuid:<filesystem UUID>`, or `mount:<mount point>` for filesystems without one (tmpfs, most network mounts). The path includes mountinfo's root field, so btrfs subvolumes sharing one UUID (`/` and `/home` on Fedora) do not collide. A drive mounted somewhere else keeps its photos. Linux only.
- **Database** (`core/db.py`): `$XDG_DATA_HOME/lumina/library.sqlite3`, WAL, one connection per thread. Schema version in `PRAGMA user_version`, one migration per version, append only; a file from a newer Lumina is refused before anything touches it. Tables: volumes, folders (the library's roots), photos (file state, availability, content id, metadata), jobs, job_failures; edits, keywords and collections came with the phases that needed them, as migrations.
- **Folders.** Adding a folder inside one already in the library adds nothing; adding one around others merges them. Removing a folder from the library forgets its photos after asking; the files are not touched. Names that are not valid UTF-8 are reported as failures and skipped.
- **Scan job** (`core/library.py`): find (new, changed by size or mtime, missing), then details (content id and exiftool metadata in batches of 50). Missing photos are marked unavailable with everything known kept, never deleted; nothing is marked missing after a cancel or below a folder that could not be read; a folder gone from a connected drive fails the job and marks its photos unavailable. Every failure is a row naming the file. Without exiftool the photos are listed and their details read by a later scan.
- **Jobs** (`qt_models/library.py`): one at a time, on a thread. At the start every connected folder is queued for a rescan and unfinished jobs (a crash) are run again; a quit in the middle leaves the job queued. A job whose drive is not connected waits for it. The mounts are read every 3 s; a drive plugged in gets its folders rescanned. Cancel stops the running job and drops the queued ones.
- **Watching.** No live file watching yet: changes are picked up at the start, when a drive is plugged in, and by Rescan. inotify needs a watch per directory and does not see changes made while the app is closed or on unplugged drives, so the scan-on-start is needed anyway; live watching can come later.
- **UI.** Sidebar with All Photos and the folders (a not-connected one is dimmed, with its drive's label in the tooltip); year, camera and lens filters; the grid, read on a thread and refreshed every 2 s while a scan writes, keeping its place; the viewer, with capture time, camera, lens and exposure in the status bar; the job's progress and Cancel in the status bar, failures listed in its tooltip. Photos on an unplugged drive keep their thumbnails, from the disk cache by content id. Thumbnails come small, medium or large (112, 168 or 280 px; the cached 320 px thumbnails stay sharp at all three on a 1x screen): three buttons by the filters, Ctrl+Plus and Ctrl+Minus, or Ctrl and the wheel over the grid; the size is remembered and the current photo kept in view.
- **Left open here, done with #5** (below): a size limit for the thumbnail cache, cancelling thumbnails for rows scrolled past, throttling very large first imports, live watching, keeping the grid's place exactly, an orientation cross-check. (The `.desktop` file is done: `data/lumina.desktop`, installed by `install.sh` with `icons/lumina.svg`.)

**Phase 3: Develop view.** Edit params and storage, linear decode and cache, proxy renderer, curve widget (draggable points, histogram backdrop), matte control, exposure/WB, undo/redo, presets, export, thumbnail invalidation on edit.

**Phase 3a as built: the engine, no UI** (`core/edit/`).

- **Params** (`params.py`): frozen dataclasses with `to_json`/`from_json`, schema `version` 1, a migration table (`_MIGRATIONS`, a test checks every version has its step), a newer document refused (`NewerParams`), bad values clamped or defaulted field by field. Fields: exposure (stops), white balance temperature and tint (-100 to 100), curves (RGB and per channel), matte (black, white, shadow desaturation), quarter turns, crop. `fingerprint()` for caches of rendered images. Presets are documents with some of the sections, applied over another edit.
- **Curves** (`curves.py`): Fritsch-Carlson PCHIP in numpy (no scipy), on sRGB-encoded values.
- **Pipeline** (`pipeline.py`): geometry first (every later step is per pixel, so cropping first gives the same image for less work), then one gain per channel (white balance: the white point moved along the black body curve, in mireds from D65, luminance kept; tint on green; exposure), then one tone LUT per channel (encode, RGB curve, channel curve, matte range, decode), then shadow desaturation, then vibrance and saturation, the HSL bands and colour grading, the vignette and the grain (all on encoded values), then sRGB out. 8-bit output through LUTs, 16-bit through interpolated tables (max error 0.03 of a 16-bit code). Full-size renders in tiles of 512 rows.
- **Source** (`source.py`): RAW decoded once to linear 16-bit sRGB primaries (camera white balance, `no_auto_bright`), other files decoded from sRGB; a ~2 MP float proxy resampled in linear light.
- **Export** (`export.py`): JPEG, PNG 8/16, TIFF 8/16, all with an sRGB ICC profile; 16-bit PNG and TIFF writers of our own (Pillow can't write 16-bit colour). Resizing to a longest side applies after the crop. Written beside the destination, then placed by an exclusive create, so a file that appears meanwhile is never overwritten; the original is refused even with Replace; a cancel or failure leaves nothing.
- **Storage**: database schema 2 adds `edits` (photo, copy number, params JSON; copy 0 is the photo's own edit, more are virtual copies) and `presets`. Edits go with their photo when its folder is removed from the library, and stay when the file goes missing.
- **Speed**, 32 MP CR3 from a 90D: decode 0.75 s, proxy 0.4 s, proxy render 25 to 70 ms (fast enough to drag controls; no GPU path needed for now), full 8-bit render 0.85 s, full 16-bit 2.4 s; exports: JPEG 2.0 s, TIFF 16 2.4 s, PNG 16 5.1 s (zlib). Peak memory about 670 MB.
- **Decided: a RAW starts plain.** A new edit has no default settings: with no edit, a RAW is the plain linear decode in sRGB, about 1 EV darker than the camera's JPEG (measured on three 90D files: 0.93 to 1.04 EV), since the camera adds its own tone curve. Exposure and the curve are the user's to set. The grid shows the camera's embedded JPEG until a photo has an edit, so a RAW looks brighter in the grid than when it is first opened in the Develop view; the Develop view should not hide that by adjusting anything.
- **Later:** HSL and the rest of Phase 5. (Straightening and mirroring came with 3b, schema 2.)

**Phase 3b as built: the Develop view.**

- **Render process** (`core/edit/session.py`, `workers.DEVELOP`): one worker process of its own keeps the open photo decoded, its proxy, and a screen-sized copy, and holds one photo at a time. Thumbnails never queue in front of a render.
- **Session** (`qt_models/develop.py`): at most one render in flight; while it runs, a newer request replaces the waiting one, so the image follows a dragged control and never falls behind. The proxy while a control moves, the screen-sized render when it stops. An edit is saved when a change is committed (a control let go, a point dropped, a preset, undo), not on every move; an edit back at no change is removed, so the photo is its original again. Undo and redo are a stack of committed states, per opening of a photo. An edit from a newer Lumina is not opened, so never saved over.
- **View** (`ui/develop_view.py`): the photo, and a card of controls: exposure; temperature and tint; the curve (RGB, R, G, B) over the histogram of the current render; matte; rotate left and right, flip horizontal and vertical, straighten (-45 to 45 degrees); crop on the photo itself, with the whole photo shown and dimmed outside the frame, thirds, and handles at corners and edges; presets (apply, save the white balance, curve and matte of this edit, delete). Toolbar while editing: Undo, Redo, Reset, Export. E edits the photo chosen in the grid or shown in the viewer; in the crop, C or Enter accepts and Escape cancels (back to the crop and straightening it had when opened, as one undoable step); C opens the crop; Escape otherwise leaves the view; the arrows step to the previous or next photo, the edit saved as it goes.
- **Controls** (`ui/controls.py`, `ui/curve_editor.py`): a slider previews while dragged and commits when let go, or 400 ms after a key or the wheel; a double click resets. The wheel moves a slider only once it has the focus (clicked or tabbed to); otherwise it scrolls the panel (#76, below). Curve: click adds a point on the curve, drag moves it between its neighbours, double click, right click or dragging it out of the square removes it; the end points move only up and down.
- **Export** (`ui/export_dialog.py`): format, depth (what the format can hold), JPEG quality, full size or a long side, folder and name, remembered. The name is never the original's own; an existing file is replaced only after asking, also when it appears while the export is written.
- **Edits elsewhere:** the grid's thumbnail and the viewer show the edit, rendered from a half-size decode (`core/edit/preview.py`). An edited thumbnail is cached under the content id and the edit's fingerprint, so a new edit is a new thumbnail; a photo on an unplugged drive shows its last edited thumbnail if there is one.
- **Fixed on the way:** selected thumbnails were tinted with the highlight colour by the style (they now look the same selected); sliders around zero no longer fill from the left.
- **Geometry, schema 2.** Edit parameters gained `flip` (horizontal, vertical) and `straighten` (degrees, clockwise), with the first real migration (1 to 2: none of either, so old edits render as before; a migration only fills in missing fields). Order: quarter turns, mirroring, straightening, crop. Straightening turns about the centre and scales up just enough to fill the frame (no empty corners; Lightroom's "constrain to image"), and samples bilinearly only the pixels inside the crop, by flat index in blocks of 256 rows. `Params.turned()` and `flipped()` give the edit that shows the result turned or mirrored, crop and all (turning swaps the two flips; mirroring negates the angle); tests check them pixel for pixel against turning and mirroring the render. Cost on a 32 MP CR3: proxy render about 100 ms with straightening (25 without), full 16-bit 2.8 s.
- **Not yet:** cancelling an export in progress. (Zoom to 100 % came with the viewer's, crop aspect ratios, the fine grid, before/after, copy and paste of settings and the choice of what a preset keeps with #25, below.)

**Phase 4: semantic search.** First-run model download, ONNX CLIP, batch embedding job, vector store choice, text search UI, "similar photos".

**Phase 4 decisions** (measured 2026-10-14 on this machine, 12 cores, Python 3.14).

- **Vector store: none.** Benchmark, 200k random 512-dim vectors, top 50: numpy over a float32 matrix in memory 12 ms a query (loaded from float16 blobs in SQLite in 0.4 s, 274 MB on disk); sqlite-vec 160 ms (416 MB, brute force too); Qdrant local mode not run (its local mode is pure-Python brute force and brings pydantic and grpc). So vectors are a table in the library database, under its migrations and safety rules, and search is one matrix product. Memory: 768 dims x 4 bytes, about 600 MB at 200k photos; search in float16 chunks if that becomes a problem.
- **Model: SigLIP 2 base, multilingual** (`google/siglip2-base-patch16-224`, Apache 2.0), because queries are in Finnish as well as English. The ONNX export is `onnx-community/siglip2-base-patch16-224-ONNX` (no licence tag of its own on Hugging Face, checked 2026-10-15; it lists Google's model as its base, so Apache 2.0 is taken to carry over; Lumina does not redistribute the weights, each user downloads them; if they are ever bundled, ask the repository for the tag or export the ONNX from Google's weights; the training data, WebLI, is unreleased and has no licence of its own on the card), pinned to revision `ba1f3b0843f24bc5417d38e19c37b287d719b2f4`, files checked by SHA-256:
  - `onnx/vision_model_fp16.onnx`, 186 MB, `a1959f7bd3993a607e48839f6d01e25b876fe76afda301b028b78eef68aabd95`
  - `onnx/text_model_fp16.onnx`, 565 MB, `711da56ada0a4aa11c7dd3320df741081a3cae4f0ae1b5e5c6d5b294738d0eb0`
  - `tokenizer.json`, 34 MB, `cb9140fae3ac5122c972d37adf83e1248471a38147ad76f8215c8872c6fd8322`
- **Why fp16.** Against fp32 on the 20 sample CR3s: fp16 vision cosine 0.999997 and 105 ms a photo (fp32 127 ms); fp16 text 0.9999994 and 21 ms a query. int8 is not usable: vision drops to cosine 0.70 and stops finding the rocks for "rocks on the shore"; int8 text (0.84) loses "kiviä rannalla".
- **Preprocessing.** Image: the preview Lumina already decodes (embedded JPEG for RAW), squashed to 224 x 224 bilinear, scaled to [-1, 1], NCHW float32 (the fp16 models take float32 in and out). Text: lowercased (SigLIP 2 was trained on lowercase text), the `tokenizers` package on `tokenizer.json` (it adds `<eos>`), padded with id 0 to 64 tokens. Output: `pooler_output`, L2-normalised.
- **Scores.** SigLIP's `logit_scale` 4.7245 (x 112.67) and `logit_bias` -16.7717 are not in the split ONNX files; they come from the original weights and are constants in the code. p = sigmoid(112.67 cos - 16.77) is a match probability: on the samples, "majakka talvella" to the sea mark 0.95, "rocks on the shore" to the rocks 0.12, "lunta ja jäätä" to the sea mark 0.006, "a dog" to anything 0.0001 or less. Results are ranked by cos; the cut-off for "no matches" is tuned in 4b on a real library.

**Phase 4 design.**

- **4a, engine without UI:** `core/models.py` (download to `$XDG_DATA_HOME/lumina/models/<name>/<revision>/`, to a temporary file, checked, then renamed; resumable; the only network code in Lumina, and it runs only when the user asked for it), `core/embed.py` (ONNX sessions, preprocessing, tokenizer; image and text), schema 3: `embeddings` (content id, model, float16 vector), keyed by content id so a moved, renamed or duplicated photo reuses its vector and a missing one keeps it, `core/search.py` (load, rank by text or by photo, combine with the grid's filters). An embed job after a scan's details step, in batches, in one worker process of its own at low priority (`os.nice`; about 8 photos a second here, 3.5 h per 100k), resumable because what is left is just the photos without a vector for the model. The unedited photo is embedded, not the edit.
- **4b, UI:** a search field over the grid (results in rank order, filters still apply), "Similar photos" from a photo, the download offer (made when the search field is first used, never at startup; the app works fully without it) and its progress, the embed job's progress in the status bar.

**Phase 4a as built: the engine, no UI.**

- **Model files** (`core/models.py`): pinned revision, size and SHA-256 per file, in `$XDG_DATA_HOME/lumina/models/<name>/<revision>/`. Each file goes to a `.part`, continues from where it stopped (HTTP Range), is checked, then renamed; a wrong file is removed, a cancel or a network error keeps the part. Installed means every file at its size. Tested against a local server; no test touches the network.
- **Encoder** (`core/embed.py`): `Encoder` (vision and text sessions loaded when first used), `encode_files` for the worker process (decodes at 512 px, encodes the batch, a PhotoError for a file it cannot read; lowers its own priority once). Measured through the app's process on the sample CR3s: 20 photos indexed in 5.8 s with the model load, 132 ms a photo warm.
- **Storage**: database schema 3 adds `embeddings` (content id, model, float16 vector or the error). A photo that could not be read is not tried again until its bytes change. Removing a folder drops the vectors no remaining photo has; a missing photo keeps its vector.
- **Indexing job** (`core/indexing.py`, kind `embed`, no folder): what is left is the photos with no vector, on connected drives, newest first, one per content id, in batches of 16. A batch that raises (a decoder crashed the worker) is tried photo by photo, so the culprit is named; when every photo of a batch raises, the encoder is broken and the job fails without marking anything. A photo gone while it ran (a drive unplugged) is passed over, not marked.
- **Search** (`core/search.py`): `Index`, the vectors in a growing float32 matrix, refreshed by row id so only new vectors are read; `rank(photos, query, floor)` within the grid's rows. Text results stop at p = 0.001 for now.
- **Service** (`qt_models/search.py`): `SearchService` next to `LibraryService`: download on request only, with progress and cancel; indexing at the start (when the model is there), after every scan and when the drives change, on a thread of its own (`workers.INDEXING`) with the encoding in a process of its own (`workers.EMBED`); searches on one thread (`workers.SEARCH`) holding the index, with the words encoded in a process of its own (`workers.QUERY`) that keeps the text model loaded (2 threads), newest search wins. Not on the search thread: loading the tokenizer holds the GIL for about 0.75 s, which froze the UI; in the process the UI does not stall at all. First text search about 1.6 s (loading the text model; the status bar says "Loading the search model…" instead of "Searching…" until a search has come back), then about 60 ms; similar photos the same. A quit leaves indexing queued; Cancel in the status bar stops scans only.
- **Fixed on the way:** `workers.submit` called back inside itself when the work was done before it returned (the relay's signal is now always queued), which made a test fail on a fast machine.

**Phase 4b as built: search in the window.**

- **Grid** (`qt_models/library_model.py`): a search (a text, or like a photo) shows the filter's rows ranked by the SearchService, only those that match; the filters still apply. It runs again when the rows are read again (a scan, a filter) and, at most every 3 s, while indexing makes more photos findable. Stepping in the viewer and the Develop view follows the ranked order.
- **Search field** (`ui/search.py`) at the right of the filter row: searches 350 ms after the last key or at once on Enter; Ctrl+F goes to it (from the viewer or the Develop view too); Escape in it or in the grid, or its clear button, shows every photo again. The filters keep their width and the field gives way.
- **Find Similar Photos** (S, and the grid's context menu): from the grid's chosen photo or the viewer's, back to the grid ranked by likeness, itself first. A chip "Like <name>" in front of the field ends it when clicked. A photo not indexed yet says so in the status bar.
- **Download offer**: the first search without the model asks, saying the size, the source and that nothing leaves the computer afterwards; Not Now fetches nothing and asks again on the next search. Progress and Cancel in the status bar; a failed download says why and that the next try continues.
- **Status bar**: "3 photos match “…”", "No photos match “…”", "20 photos like …", with "more as indexing goes on" while it runs; indexing has its own progress and Cancel beside the scan's.
- **Not yet:** the text cut-off is still p = 0.001; on the samples "kiviä rannalla" keeps 19 of 20 photos (rocks first). Tune it on a real library. A match score in the cell or tooltip, and searching within a selection, if wanted.

**Phase 5: later.** HSL and colour grading, crop tools, lens corrections, GPU rendering, soft proof, packaging (AppImage/Flatpak), keywords and collections, ratings.

**Phase 5a as built: thumbs up and down, for going through new photos before editing.** The base that ratings, keywords and smarter filters build on.

- **Flag** (schema 4): `photos.flag`, thumbs up (1), none (0) or thumbs down (-1). One per photo, not per virtual copy. Kept while the file or drive is missing and when the file changes, as edits are; never written to the original (an XMP sidecar can come with ratings and keywords).
- **Setting it**: P thumbs up, X thumbs down, U clears; the same key again clears it too. Two buttons in the toolbar (filled in the flag's colour while set) and the grid's context menu. In the grid it is for every chosen photo (all get it unless all have it already); in the viewer for the photo shown. Ctrl+Z and Ctrl+Shift+Z undo and redo flag changes in the grid and the viewer, also of photos no longer shown; in the Develop view they stay the edit's. The keys are the grid's and the viewer's, so typing in the search field does not flag.
- **Showing it**: a badge on the thumbnail's corner (a thumb in the theme's success or danger colour on a card-coloured disc). Thumbs-down photos are dimmed (default), shown as any other, or hidden, from the button by the thumbnail sizes; the choice is remembered. Hidden ones are left out of the grid and the viewer's stepping, and the status bar says how many the flags hide. The viewer's status bar names the flag.
- **Flag filter**: all, thumbs up, not flagged, thumbs down, beside the year, camera and lens. "Not flagged" is the pile still to go through. A thumbs-down photo asked for is not dimmed.
- **Flagged out of the view**: the flags narrow the rows in the model (`qt_models/library_model.py`), not in the query, so flagging is instant. A photo flagged out of the view (a thumbs down while they are hidden, or any flag under "Not flagged") stays, dimmed if it is a thumbs down, until the user moves on: another current photo in the grid, the next photo in the viewer. Then it leaves the grid as a removed row, so the selection stays.
- **Next photo after flagging**: opt-in, in the settings window (#13; at first it was in the same button's menu). In the viewer only; clearing a flag does not step on.
- **Edit filter**: all, edited, unedited, a fourth combo beside the flag filter. "Edited" is a photo with an edit of its own (`PhotoRow.edit`; saving an unchanged photo stores none); a virtual copy does not count. Like the flag filter it narrows the rows in the model, not in the query. A photo whose edit changes while the filter is on (edited under "Unedited", reset under "Edited") stays, as one flagged out of the view does, until the user moves on. The status bar's "hidden by flags" counts only what the flags leave out of what the edit filter lets through.
- **In the Develop view (#17)**: P, X and U flag the photo being edited, with the two toolbar buttons, which show there too; the status bar names the flag. Ctrl+Z stays the edit's: a flag changed there is undone from the grid or the viewer afterwards (one history in the model, so nothing is lost by leaving). No stepping on after flagging while editing: stepping saves the edit and decodes the next photo. The Develop view's own keys do not clash (its sliders take no typing).
- **Stars (#16), schema 5**: `photos.rating`, 0 to 5, apart from the flag (a photo can have a thumbs up and three stars), kept as the flag is. Keys 1 to 5 set it, 0 clears it and the same key again clears it too; in the grid for every chosen photo (all get it unless all have it), in the viewer and the Develop view for the photo shown; a Rating submenu in the grid's context menu, and five stars in the toolbar beside the flag buttons (`ui/stars.StarRating`): they show the rating of the photo shown or chosen (none when the chosen photos differ, as neither flag button shows as set), hovering shows what a click gives, and clicking the star the rating is at clears it. Shown as small stars in the theme's warning colour on a card-coloured pill at the thumbnail's bottom left corner (the flag's badge is at the right), only for rated photos, and in the viewer's and the Develop view's status bar. Filter: any, 1 star or more up to 5, not rated, beside the flag filter; like the others it narrows the rows in the model, a photo rated out of the view stays until the user moves on, and the status bar's "hidden by flags" does not count what the rating filter leaves out. One undo history for flags and ratings (`library_model._undo` holds (field, values before)), so Ctrl+Z undoes them in the order they were made. "Next Photo After Flagging or Rating" (the same option) steps on in the viewer after a rating, not after clearing one.
- **Not yet:** colour labels, sidecars (#53, below), a count per flag or rating in the filters. Keywords and collections are #52, below.

**Settings window (#13).** `ui/settings_dialog.py`, opened with Ctrl+, or the button at the right end of the toolbar. As filehouse's: a change is made as it is picked (no OK, only Close), and what is chosen stays in QSettings through `ui/settings.py`. Options that belong to one control stay with it (the grid size, what to do with thumbs-down photos, the export dialog's choices).

- **Culling**: go to the next photo after flagging or rating.
- **Search**: whether the model is there, being downloaded or being deleted, the folder it is in, Download, and Delete… (asks first). Deleting stops a download or indexing, then removes the model's folder on the indexing thread (`core/models.remove`, which leaves anything beside it alone) and drops the text model the searches keep loaded. The vectors stay: the same model downloaded again does not index again. "Download again" is Delete then Download.

**Thumbnail cache limit (#5).** The cache is limited in size (setting, in the settings window; default 4 GB, 0 for none) and pruned in the background: `thumbs.prune(root, limit, keep)` deletes the thumbnails used longest ago, down to 90 % of the limit, those of the content ids in `keep` last. A thumbnail's use is its file's time: written when it is made, and noted on a read when the note is over an hour old (`ThumbnailCache.get`), not on every read, which a scrolling grid makes thousands of. `keep` is the photos that can't be read now (`db.offline_content_ids`: marked unavailable, or on a drive not mounted), since their thumbnails can't be made again until the drive is; they do go, oldest first, when the others are not enough. Only `.webp` thumbnails are deleted, and `.part` files a crash left (over an hour old; a newer one is being written): never a photo, and nothing outside the cache's own folder. It runs on a thread of its own (`workers.CACHE`) with a database connection of its own, at the start, after a scan when the last was over ten minutes ago, and when the limit is changed (`LibraryService.set_thumbnail_limit`); as it only deletes what can be made again, it is not a persisted job: the next start does it again. The settings window applies a new limit after a moment without a change (and when it closes), so spinning it down does not delete on the way. Also fixed: `job_changed` told the phase the database had when the call was delivered, so a quick phase was sometimes never told (a flaky test); it tells the one the scan reported.

**HEIC and HEIF (#42).** `.heic` and `.heif` are photos (`core/images.py`): `pillow-heif` is a dependency and registers its opener with Pillow in every process that imports `core/images` (the workers re-import it); without it, those files are not listed rather than listed and not shown (`images.HEIC`). Everything else reads them as it reads a JPEG.

- **Orientation**: the opener turns the image by the container's rotation or the EXIF tag and sets the tag to 1, so `exif_transpose` is a no-op and a photo is not turned twice (tests for 1, 3, 6 and 8, and for which corner is which).
- **Colour**: a photo with an embedded ICC profile that is not sRGB is converted to sRGB (`images.upright_srgb`, lcms through `ImageCms`, relative colorimetric): an iPhone's Display P3, a camera's Adobe RGB. It is for every JPEG, PNG, TIFF and HEIC, not only HEIC, and in the grid, the viewer and the edit's decode (`edit/source.py`); a photo without a profile, or with sRGB's, is as it was. Done after the turn, since the conversion drops the EXIF. Without monitor profile management the screen is taken to be sRGB, as before; a wide-gamut screen shows the converted colours as sRGB.
- **Depth**: decoded at 8 bits, also a 10-bit photo (pillow-heif's default), so the edit has what a JPEG has. Not kept: more bits, HDR gain maps, the depth image and Live Photo videos (the `.mov` beside it is not a photo here).
- **Speed**: a 12 MP HEIC takes about 0.5 s to decode at any size, a 24 MP one about 0.9 s (a JPEG at thumbnail size 30 ms, through `draft`). So the grid reads the thumbnail inside the file (an iPhone 17 Pro Max's is 416 x 312) in about 20 ms: `draft` with pillow-heif 1.8 or newer takes the smallest one that covers the photo at the size asked, as stored (`images._draft_box`; not the square, which 416 x 312 does not cover), and only one turned like the photo and in its profile. On the real samples it is upright and in the same colours as the photo read in full, a little softer. Larger sizes (the search's 512, the viewer) decode the photo.
- **Metadata**: exiftool reads a HEIC's EXIF as a JPEG's (test with a made file).
- **Real files**: `tests/core/test_samples.py` runs on the HEICs in `tests/samples/` (iPhone 17 Pro Max, 12 and 24 MP, portrait and landscape, Display P3, with an HDR gain map that is not used): shown upright once (the opener's turn agrees with the EXIF's orientation, and exiftool's orientation, still 6, is stored but not applied), the grid reads the thumbnail inside it, Apple's P3 profile is one lcms converts, the edit's decode is the upright full size, the metadata is read, and the files are left as they were.

**Basic tone controls (#19), schema 3.** Lightroom's Basic panel: contrast, highlights, shadows, whites and blacks, -100 to 100 each, under Exposure in the Develop view.

- **One curve** (`core/edit/basic.py`): a monotone PCHIP through fixed points on the sRGB-encoded scale (deep black, shadows, quarter, middle grey, three-quarter, bright, white, and points past white); each control moves some of them up or down. At zero the points lie on y = x, so the curve changes nothing, and a control moved by one changes the render by at most a few 16-bit codes: no jump when the Basic controls come into use. The points are kept rising whatever the controls do together, so the curve never falls; black stays black (lifting it is the matte's). The curve is folded into the tone LUT, before the RGB curve, so it costs nothing per pixel: a 2 MP proxy renders in about 55 ms with it, as with a curve; the LUT is built in 4 ms.
- **Headroom**: with any Basic control in use the tone LUT spans linear light up to 4 times white (two stops), scaled into [0, 1] with the channel gains, so light exposure pushed past white is still there for the curve. Highlights below zero bring it back (at -100, all two stops), whites below zero about one stop, together never past the end. The points past white follow a straight line as they are brought back, so the recovered highlights keep their detail evenly rather than flattening at the end. With every Basic control at zero, light past white is clipped at white as before. Positive whites and highlights clip more.
- **Params**: a `basic` section; migration 2 to 3 adds it at zero. Presets saved from the Develop view keep it, with the white balance, curve and matte.
- **Not yet, and known**: the curve acts per channel as the RGB curve does, so compressing bright colours also desaturates them a little (a warm sky towards grey with highlights at -100); Lightroom keeps hue and saturation there. A luminance-based variant would fix that, at the cost of the tone step being one LUT per channel. The amounts each control moves are a first tuning, to be adjusted on real photos.

**Vibrance and saturation (#20), schema 4.** A `colour` section, -100 to 100 each, under COLOUR in the Develop view (between white balance and the tone curve).

- **Step** (`core/edit/colour.py`): after the tone step and the matte's shadow desaturation, on sRGB-encoded values. Each pixel's colour is scaled about its own luma, so brightness and a grey stay where they are. Saturation scales every colour by 1 + amount (-100 is monochrome, +100 doubles the distance from grey). Vibrance scales by 1 + amount x weight, the weight being (1 - chroma)^2 (muted colours move most) times a skin factor: hues from red-orange to orange-yellow (red over green over blue, green's share of red over blue between 0.17 and 0.75, soft edges) keep 40 % of the effect. Below zero it is the same weight the other way round: muted colours go to grey first, strong ones and skin stay.
- **No clipping**: a boost is cut to what the pixel can take (brightest channel to 1, darkest to 0), so a colour at the edge of the range stays where it is and the hue never shifts from one channel clipping. Zero skips the step, so an unedited photo is byte for byte as before.
- **Speed**: done on 32-row chunks (the temporaries stay in cache; on whole 512-row tiles it was five times slower). A 2 MP proxy renders in 70 to 90 ms with it (30 ms without), 32 MP at full size in about 1.9 s (0.5 s without, 8 bits). With a colour control in use 8 bits no longer go through the single output LUT, as the step needs the encoded floats.
- **Params**: migration 3 to 4 adds the section at zero; presets saved from the Develop view keep it.
- **Not yet, and known**: the skin test is by hue only (no check on brightness or on a face being there), so a sunset's orange is protected too; the amounts are a first tuning, to be adjusted on real photos. A hue-preserving saturation in a perceptual space such as Oklab is still to try.

**HSL and colour grading (#21), schema 5.** An `hsl` section (eight bands, each hue, saturation and luminance, -100 to 100) and a `grading` section (a wheel for shadows, midtones and highlights, each with hue 0 to 360, saturation 0 to 100 and luminance -100 to 100, plus blending 0 to 100, default 50, and balance -100 to 100). In the Develop view: HSL under COLOUR, with a button per band (R O Y G A B P M, each with its border in the band's own hue, filled with it when chosen, computed from the band's centre rather than taken from the theme) and three sliders for the band chosen; COLOUR GRADING with a button per range, three sliders, then blending and balance. Presets keep both sections.

- **Bands** (`core/edit/hsl.py`): the hue of each pixel (from the order of its encoded channels, as HSV; read off a table at half-degree steps) says how much of each control applies. The eight centres sit at 0, 30, 60, 120, 180, 240, 270 and 300 degrees; a control is stepped smoothly (smoothstep) from its centre to its neighbours', so a band reaches no further than the centres either side and a colour no adjusted band reaches is left alone, byte for byte. The effect fades in with the pixel's chroma (nothing at grey, full at 0.06) so noise in near-greys does not turn into colour, and greys stay grey.
- **What a band does**: hue turns the colour about the grey axis, luma kept, up to 30 degrees at 100 (a rotation in the plane of colours with no luma, `colour.QUARTER`; red goes towards orange, not magenta, when positive); saturation scales the distance from grey by 1 + amount; luminance blends towards white or black by up to half. Whatever the turn or scale, a colour is cut back towards grey to fit in range, so no channel clips and the hue does not drift.
- **Grading** (`core/edit/grading.py`): the three weights follow the encoded luma and add up to one; balance moves the two edges (0.3 and 0.7 at zero; positive gives more of the photo to the highlights), blending the width of the transition (0.04 to 0.34 either side of an edge). A wheel's tint is a colour with no luma in the direction of its hue, up to 0.25 long at saturation 100, added in proportion to the pixel's weight for the range and cut to what the pixel can take, so black and white stay as they are and the luma does not change. A wheel's luminance lightens or darkens its range by up to half.
- **Order and speed**: vibrance and saturation, then the bands, then grading, each on the same 32-row chunks of encoded floats. A 2 MP proxy renders in about 0.15 s with the bands or grading in use (0.04 s without a colour step, 0.08 s with vibrance and saturation); full-size at 32 MP in about 3 s. Making the hue index cheap took most of the work (no `np.mod`, planes made contiguous, tables starting at hue -60): a reduction over the last axis of three is the slowest thing numpy does here.
- **Saving a preset** (`ui/preset_dialog.py`): a name and a checkbox for each section of the edit (exposure, white balance, Basic, vibrance and saturation, HSL, grading, tone curve, matte, then rotation, mirroring, perspective, straightening, crop). A first preset keeps the look (white balance to matte), not this photo's exposure or its framing; after that the dialog starts with what was ticked last. Saving needs a name and at least one part, and the button says Replace when the name is a preset's already.
- **Not yet**: the grading wheels are sliders (hue, saturation), not round pickers; a target-adjustment tool (drag on the photo to move the band under the pointer); a bands' reach that follows hue in a perceptual space, so that blue at 240 degrees of encoded sRGB and "blue" to the eye agree; the amounts are a first tuning.

**Vignette and grain (#22), schema 6.** A `vignette` section (amount -100 to 100, midpoint and feather 0 to 100, default 50 each) and a `grain` section (amount 0 to 100, size 0 to 100, default 25), under EFFECTS in the Develop view, after the matte. Presets can keep either; the preset dialog lists both and a first preset keeps them.

- **Where** (`core/edit/effects.py`): the last steps before the output, on the encoded values, working from the photo as rendered, after the crop and straightening, so they follow the frame. `render` hands each tile's first row on, so the steps know where they are in the whole photo.
- **Vignette**: an ellipse with the frame's proportions, 0 at the centre and 1 at a corner, smoothstepped between two radii (midpoint is where it is half there, 0.2 to 1.0 of the way to a corner; feather the half-width of the way in, 0.05 to 0.5). Below zero it multiplies the colour down (-100 is black at the corners), above zero it blends towards white (+100 is white). In shares of the frame, so a proxy and a full render have the same vignette.
- **Grain**: value noise on a lattice, each point hashed from its position and a fixed seed (murmur3's finaliser; no random state), smoothly interpolated and normalised for the strength the interpolation takes off, so a render is the same every time and in any tiling. One value for all three channels (brightness grain). A grain is `size` in shares of the photo's long side, 1/2500 to 1/250 (3 to 32 px on 8000), never under one pixel, so a proxy has the grain of the full render to the extent a pixel allows (the finest grains are held to one pixel on a small render). Amount 100 is a standard deviation of 0.08 on the encoded value. The grain is weaker towards black and white (35 % of its strength at the ends of the range, then gone over the last 3 %), and nothing at pure black or white, which stay clean instead of being lifted by clipped noise.
- **Speed**: a 2 MP proxy renders in 0.07 to 0.1 s with either (0.04 s without a colour step); 32 MP at full size in 1.4 to 1.7 s.
- **Not yet**: grain roughness (a second scale of noise), colour grain, vignette roundness and highlight priority, a vignette that stays on the uncropped photo (a "pre-crop" mode).

Ctrl+Up and Ctrl+Down step through the photo's own edit and its copies, in the viewer and the Develop view; stepping to another photo starts at its own edit, and Escape from the Develop view returns to the viewer on the same copy.
- **Editing and exporting**: `DevelopSession.open(photo_id, path, copy)`; every commit saves to that copy. A copy is never removed by Reset or by matching the baseline (the photo's own edit is: a copy that is reset stays as the original); it is deleted only by Delete Virtual Copy (asks first; the session is closed first so nothing is saved over it). A copy of an unedited RAW file holds the identity, so opening it applies the RAW baseline (lens corrections, camera look) as a new edit does. Export uses the copy's edit and suggests `name-copy2.jpg`.
- **Other features**: flags, ratings, keywords, collections and search are per photo, as before. The edit filter looks only at the photo's own edit. Copy and paste of settings from the Develop view use the edit shown, so they follow the copy; pasting in the grid goes to a photo's own edit. XMP sidecars already carried all copies.
- **Copies in the grid**: a click on the diamond (or Show Virtual Copies in the grid's menu) opens the photo's copies as cells after it, a click again closes them (`LibraryModel.toggle_copies`; kept for the session only). A copy's cell is the photo's `PhotoRow` with `copy` set and the copy's edit, so its thumbnail is the copy's; its diamond shows its own number, and it has no stack badge. A cell is identified by (photo id, copy); `row_of(id)` is still the photo's own cell. Flags, ratings and keywords act on the photo whatever cell is chosen. Enter or a double click opens the copy of the cell, and stepping in the viewer goes cell by cell. Delete Virtual Copy is in the menu of a chosen copy's cell (asks first).
- **Not yet**: a copy chosen for export or paste from the grid, naming copies, collections of copies.

**Stacks, schema 11.** Stacks of photos only. Virtual copies are not stacked (they open as cells of their own after the photo, see above).

- **Storage** (`core/db.py`): `stacks` (id, `key`, collapsed) and `photos.stack_id` + `stack_position`; a photo is in at most one stack, the top is the member with the lowest position. Per library like flags and keywords, kept while a file or drive is missing, in the backup (it is the database). `make_stack(ids)` (the first on top, collapsed; a photo already stacked leaves its old stack), `unstack`, `leave_stack` (some photos out, the rest stay stacked and the next is the top), `set_stack_top`, `set_stacks_collapsed`. A stack of fewer than two photos is no stack: removing a folder, or stacking a photo away, dissolves it (`_tidy_stacks`). Made by hand, or by Stack Bursts (below); #61 later adds near-duplicates across the library.
- **Sidecars**: a sidecar holds one photo, so each member's carries the stack's `key` and the photo's position (`lumina:Stack`, `lumina:StackPosition`; the sidecar version is unchanged, an older Lumina ignores them). Reading the sidecars of a library whose database was lost puts the stack together from the keys. Stacking, unstacking and a new top note every photo they touch as changed; collapsing and expanding do not (it is how the library is shown, and stays in the database). A stack with one photo meanwhile, while the sidecars are read one by one, is kept, and shown as no stack.
- **Grid** (`LibraryModel._fold`, `STACK_ROLE`): collapsed, a stack is one cell showing its top; expanded, the top and after it the members that pass, in order. A collapsed stack's top has two more sheets peeping out below and to the right of it (`badges.paint_stack_cue`), so the cell looks like a pile. Stack (Ctrl+G, two or more chosen photos), Unstack (Ctrl+Shift+G), Remove from Stack (menu), Expand or Collapse Stack (Ctrl+Alt+G), Set as Top of Stack (menu), in the grid's menu and keys. Flags, ratings, keywords and the rest act on the photos chosen, so on a collapsed stack on its top photo only. The stacks are those of the photos the folder or collection shows: a folder showing only some of a stack's photos has the first of them as its top.
- **Stepping and counts**: the viewer and the Develop view step through the grid's rows, so a collapsed stack's hidden photos are skipped, and "12 of 340" and the status bar count the cells shown. "Hidden by flags" does not count what a collapsed stack folds away.
- **Filters and search**: a stack is shown when its top photo passes every filter and the search; a member that passes while the top does not is not shown. Expanded, a stack shows its members that pass.
- **Stack Bursts** (#61, `core/bursts.py`; grid menu): on request, not after a scan, so nothing is rearranged unasked. Over the photos chosen, or all shown when fewer than two are. A photo joins the run before it when it was taken at most 3 s after that photo's time and the cosine of their search vectors is at least 0.85 (both to be tuned on real libraries); a photo without a vector or already in a stack is left alone and ends the run. The top is a thumbs up, else the most stars, else the first, never a thumbs down while another is there; the rest stay in time order. Stacks come collapsed. Undo is Unstack.
- **Find Duplicates** (#61, `core/similar.py`, `ui/similar_dialog.py`; Find Duplicates… in the grid's menu): on a thread, in the photos the grid showed when it was opened (a folder, a collection; a snapshot of their ids) or in the whole library, as the dialog's Look in box says (only the whole library when the grid shows every photo). - **Not yet**: stacks of virtual copies, nested stacks, a stack's expanded state per view.

**Texture, clarity and dehaze (#24), schema 7.** A `presence` section (texture, clarity, dehaze, -100 to 100 each), under PRESENCE in the Develop view after the Basic sliders. Presets can keep it. First step that looks at the pixels around each one, so the render changed shape, and OpenCV (`opencv-python-headless`) is now a dependency (for the blurs; it also serves HDR merge and panoramas, #27 and #28).

- **Two passes** (`pipeline._render_in_two_passes`): when texture, clarity or dehaze is in use, the first pass does everything that treats a pixel on its own and keeps the photo as 16-bit sRGB (a third of the memory of float32: 270 MB at 45 MP), the second takes it in tiles with extra rows beyond each (`detail.layout` says how many), applies the steps, then the vignette and grain, then the output encoding. The first pass uses the exact interpolated tables for 8 bits too, so a photo looks the same at either depth. Without those controls the render is the single pass as before.
- **Clarity and texture** (`core/edit/detail.py`): a Gaussian blur of the encoded luminance says what the neighbourhood is; the difference is the detail at that size; adding more of it (or less, below zero, which softens) is the effect. Clarity's sigma is 1.5 % of the long side (reaching features up to about 120 px across at 1200 px), texture's 0.12 %. The change is added equally to all channels, so a pixel's colour stays and its brightness moves. The detail goes through a soft limiter (ceiling 0.07 for clarity, 0.10 for texture, at 100) so a hard edge grows a modest halo, not a glare; clarity keeps 30 % of its strength at black and white. A large blur is made on a copy a power of two smaller (so its sigma there is at least 3 px) and scaled up: a hundredth of the work, and the tile must start at a multiple of that factor, which `layout` returns as `align`. A 2 MP proxy renders in 0.06 to 0.08 s with either (0.02 s without), 32 MP in about 1.7 to 1.9 s each.
- **Dehaze** (`core/edit/dehaze.py`): dark channel prior. The air's colour and the transmission are worked out once for the whole photo, on a copy of it 512 px on the long side (the brightest 0.1 % of the dark channel give the air; the transmission is 1 minus the dark channel of the photo over the air, refined with a guided filter), so the result does not depend on the tiling and needs no extra rows; each tile reads its part of the map, scaled up, and recovers the scene as (pixel - air) / transmission + air. At 100 it takes out 90 % of the estimated haze, never letting less than 15 % through. Below zero it mixes the photo towards the air's colour, the same everywhere (up to 45 % at -100): without depth there is nothing to follow.
- **Not yet**: dehaze works on the encoded values, not on linear light; the transmission map is soft (it follows edges only as far as a guided filter on a small copy can), so a hard edge in depth, a tree against a hazy sky, is not followed exactly; clarity and texture work on the luminance only, so they do not sharpen the colour; the amounts are a first tuning.

**Sharpening and noise reduction (#23), schema 8.** A `sharpening` section (amount 0 to 150, radius 0.5 to 3 px, detail 0 to 100 default 25, masking 0 to 100) and a `noise` section (luminance 0 to 100, detail 0 to 100 default 50, colour 0 to 100), under SHARPENING and NOISE REDUCTION after PRESENCE. Presets can keep either. They use the same two-pass render as texture and clarity, in the order dehaze, noise reduction, clarity and texture, sharpening, then the effects.

- **Scale** (`render(..., full=(width, height))`): sharpening's radius and noise reduction's sizes are in pixels of the full-size photo, so a render of a smaller copy (the proxy, the screen's, a thumbnail's, an export made smaller) is told what the full size is and uses the radius it would have at its size (`pipeline._scale`, the render's longest side over the full render's). The session, the viewer's and the grid's edited previews and the export all pass it; without it (the tests) the image is taken to be the full size. A sharpening radius under a third of a pixel does nothing (a blur that small does not), and noise reduction does nothing below a third of the full size, where the noise has been averaged away: so the Develop view, which shows the photo fitted, shows little of either, while the viewer at 100 % and the export show all of it.
- **Sharpening** (`core/edit/sharpen.py`): an unsharp mask on the encoded luminance, the change added equally to all channels. Detail sets a soft limiter on the mask (ceiling 0.02 at 0 to 0.32 at 100: at 0 a strong edge gets a thin line of contrast, at 100 the plain mask, halos and all). Masking weighs the sharpening by how steep the luminance is around the pixel (Sobel of a lightly blurred copy, in luminance per full-size pixel), from nothing below half a threshold to all of it above one and a half, the threshold running 0.002 to 0.1 over masking 0 to 100: noise and flat areas are not sharpened, edges are. Under it a 2 MP proxy renders in 0.06 s, 32 MP in 1.5 s.
- **Noise reduction** (`core/edit/denoise.py`): luminance and colour apart. Brightness noise goes through OpenCV's bilateral filter on the luminance (spatial sigma 2 px, range 0.02 to 0.12 over the amount), the change scaled by the amount; detail puts back up to 60 % of what the filter took out. Colour noise is reduced on a copy a quarter the size (as codecs treat colour): the red and blue differences from the luminance are made smaller, put through a bilateral filter there (range 0.04 to 0.12, spatial sigma up to 12 px at full size), scaled up, and a pixel takes the result only where it is within 0.08 of its own value, so a real colour edge, which the scaling up softens, is bled across by 0.05 at most in a pixel or two. The luminance is left as it was, the green rebuilt from the weights. A tile must start at a multiple of 4 rows (`align`). 2 MP in 0.11 s, 32 MP in 2.1 to 2.4 s; everything on, 0.2 s and 4.6 s.
- **Not yet**: no luminance contrast or colour smoothness for noise reduction, no non-local means; sharpening is not made for an output size (print or screen), only the radius follows the scale; the amounts are a first tuning on synthetic noise, to be adjusted on real photos.

**Lens corrections (#55), schema 9.** A `lens` section: `enabled` (off in every edit made before, and in `Params()`), `distortion`, `vignetting` and `aberration` (0 to 100, default 100) and the `profile`. Under LENS before CROP & ROTATE: a switch, the lens it matched (Choose... lists those that fit the camera), three amounts.

- **Source** (`core/lensdb.py`): lensfun's XML, read here; no `lensfunpy` and no native library (its wheels exist, but the formulas are small, the maps have to join the straightening's, and the data is the point). The data is not shipped (CC-BY-SA, and it changes): it is the distribution's (`dnf install lensfun`, `/usr/share/lensfun`), a newer copy from `lensfun-update-data` (`~/.local/share/lensfun/updates`), or `$LUMINA_LENSFUN`; an earlier folder wins. Parsing all of Fedora's takes 0.3 s, once per worker process. Without any, the LENS section says so and nothing changes.
- **Matching**: the camera by model (exiftool's `Model`, or lensfun's alternative names) gives crop factor and mount; the lens by its name as exiftool wrote it (`EF-S18-135mm f/3.5-5.6 IS USM` is `Canon EF-S 18-135mm f/3.5-5.6 IS USM`: letters and digits only, 0.85 similar or better, focal length within the lens's calibrated range), among the lenses the mount takes (an EF-S body takes EF lenses too, from lensfun's `<compat>`), rectilinear only (fisheyes are left alone), calibrated on a sensor no smaller than the camera's.
- **The profile is in the edit.** `LensProfile` holds the numbers for this lens at this focal length and aperture (distortion model and terms, TCA terms, vignetting terms, the sensor scale), so an edit renders the same whatever lensfun's data says later, and thumbnails, exports and the Develop view need no database to render it. Between calibrated focal lengths the terms are mixed linearly (lensfun uses a spline; at a focal length between two measurements the maps differ by up to about 1 px at 600 px wide, less than the measurements' own error); vignetting takes the measurements at the nearest distance (1000 m when not known: the photo table has no focus distance) and mixes the two nearest in focal length and aperture. A profile is not part of a preset: it is of one lens.
- **Formulas** (`core/edit/lenscorrect.py`), checked against lensfun 0.3.4 through `lensfunpy` (maps agree to 0.1 px at the calibrated focal lengths, vignetting to 0.3 %): radii in half the shorter side divided by the profile's scale (lens crop factor over camera's); ptlens, poly3 and poly5 distortion; TCA `Ru (b Ru^2 + c Ru + v)` for red and blue, first, then distortion; vignetting `1 + k1 r^2 + k2 r^4 + k3 r^6` with r in half the diagonal, divided out.
- **In the pipeline**: geometry, after the quarter turns and before the crop's box is taken. Distortion, TCA and the straightening are one `cv2.remap` per 256 rows (three for TCA, one per channel), only for the pixels the crop needs; zoomed in just enough that no border shows (`autoscale`, a bisection on the edge). Vignetting multiplies the samples, by the gain at the place they came from. That can lift the corners past the white of the photo as shot, which a uint16 would clip, so the result is divided by the gain at the corners (`headroom`) and `_per_pixel` multiplies it back with the exposure. The lens works in the turned frame, so a quarter turn does not change it.
- **New edits start corrected**, for a RAW file whose lens is known (a camera's JPEG has its own correction): the session's `_baseline` is `Params(lens=on)`, what a Reset goes back to; looking at a photo saves nothing, and an edit equal to the baseline is no edit. Edits already made keep the lens off. A photo opened as a JPEG can have the lens switched on by hand.
- **Not yet**: the lens of a photo copied from another is not copied with settings; HDR and panorama frames are not corrected (#49); no manual lens (focal length and distortion typed in); fisheye and panoramic lenses; the camera's focus distance (vignetting at close range); sensor crop modes (a 4:3 or 16:9 crop of the sensor changes the frame the normalisation assumes); the corrections of the camera's embedded JPEG are not compared with ours on a real CR3 yet (no samples here have a known lens).

**Perspective (#26), schema 11.** A `perspective` section: `vertical` and `horizontal`, -100 to 100 (0 is off). Two sliders under Straighten in CROP & ROTATE, with the fine grid while they move. Positive vertical widens the top of the photo (it corrects a shot tilted up at a building), positive horizontal its right side.

- **A turned view** (`core/edit/perspective.py`): the photo is a plane a focal length (its diagonal, a normal lens) from the camera, and the correction is the homography of turning the camera, K R K⁻¹, with R the rotation by the vector (vertical, horizontal, 0) times 20° per 100 (a rotation vector, not two turns one after the other, so the order does not matter and turning or mirroring an edit stays exact: `Perspective.turned` and `flipped`; tests compare them with turning and mirroring the geometry). The turn moves the middle of the photo; the matrix puts it back.
- **Order**: quarter turns and mirroring, lens, perspective, straightening, crop. The straightening's turn and scale and the homography are one matrix from the result's pixels to the photo's (`source_matrix`), so there is one resampling: `cv2.warpPerspective` of the crop's box (bilinear, 1/32 pixel steps), or with a lens the same matrix inside `lenscorrect.resample`, which already samples a coarse map. Without perspective nothing changes: the old straightening and lens paths run as before.
- **Filling the frame**: the corrected photo is not a rectangle, so the scale that leaves no empty corner is found by bisection on the four corners (`fill_scale`; a projective map keeps lines straight), about the middle of the photo, not the best-fitting centre. Straightening alone keeps its formula. On a 3:2 photo a vertical keystone of 50 or 100 zooms in 3 percent, 30 vertical and 30 horizontal with a 5° straightening 17. Tests check that every pixel is sampled from inside the photo and that a little less zoom would not be.
- **Tests**: a vertical keystone against the geometry of the tilted plane worked out apart from the code (a ramp image, whose bilinear samples say where they came from), the horizontal one against the vertical one across the diagonal, turning and mirroring in all eight orientations, the crop, the region render, a lens that does nothing, migration 10 to 11, presets.
- **Cost** (24 MP, 16-bit): about 20 ms to warp the whole photo, the proxy 5 ms.
- **Not yet**: no automatic upright (finding the lines), no rotation of the correction about another point, no aspect-ratio slider; the fill scales about the middle, which wastes some of an asymmetric correction.

**Camera profiles (#56), schema 10.** A `profile` section: `id` ("libraw", "standard" or a stored profile's) and `name`. Under PROFILE after PRESETS: the profile (a list of Lumina Standard, Neutral (LibRaw) and the camera's DCPs), Add... (any .dcp), From Camera JPEGs, Colour Checker....

- **Decode** (`source.raw_camera`, `load_for_edit`): an edit's RAW decode is in the camera's own colours (rawpy `output_color=raw`, white-balanced as shot), with its `CameraColour`: LibRaw's matrix to sRGB, rebuilt as LibRaw makes it from Adobe's (`rgb_xyz_matrix`: the camera's colours of the sRGB primaries, rows made to sum to 1, inverted; a DNG's own `color_matrix` where there is none), the camera's white and Adobe's XYZ -> camera matrix. Through LibRaw's matrix it is LibRaw's sRGB decode to the rounding (1/65535; 13/65535 in 16-bit sRGB output near black, where the encoding is steep). HDR, panorama and the viewer keep the sRGB decode. A photo in sRGB has no `CameraColour` and no use for a profile.
- **Existing edits do not change**: the migration (9 to 10) gives them "libraw", and so does `Params()`. A new edit of a RAW file starts with the camera's profile: the first DCP for its camera in the user's folders, Lumina's own (`profiles/user`), then RawTherapee's (`/usr/share/rawtherapee/dcpprofiles`, 161 cameras with the 90D among them), leaving out ColorChecker ones (they are for one light); else Lumina Standard. Lumina does not ship profiles (Adobe's and RawTherapee's are theirs).
- **DCP** (`core/dcp.py`): read and written (TIFF-like, "IIRC"), all of RawTherapee's read and survive writing. Found by camera with RawTherapee's model aliases (Kiss, Rebel). An edit names a profile by content: it is copied into `profiles/store/<sha256[:16]>.dcp`, so the edit renders the same if the file changes or goes. A missing stored profile renders as Lumina Standard.
- **Applying** (`edit/colour_profile.py`, the DNG specification's chapter 6): colour and forward matrices mixed by inverse colour temperature of the white (iterated from D50, McCamy's temperature); forward matrix, or the colour matrix's inverse and Bradford; then in linear ProPhoto the hue/saturation maps (mixed the same), the look table and the tone curve by Adobe's RGB tone method (keeps hue). A profile with no tone curve gets Lumina's, as Adobe's software gives one its own. Everything after the matrix is made into a 49^3 table over sRGB-encoded ProPhoto once per profile (0.1 s) and looked up with two OpenCV remaps (mean error 0.08/255, a few levels where a channel is at zero at the edge of sRGB). The edit's white balance and exposure are folded into the matrix (in sRGB terms, by similarity), so a profile costs a 3 x 3 matrix and the table: 32 MP renders in 1.0 s (LibRaw's 0.3 s), the proxy in 0.055 s (0.018 s).
- **Lumina Standard**: LibRaw's matrix, saturation x 1.08 and a tone curve three quarters of the way from a plain one to the curve fitted from the 90D's own JPEGs. Against the 90D's embedded JPEGs (mean of the middle of the frame, 8-bit levels): LibRaw neutral 22, RawTherapee's 90D DCP 11, Lumina Standard 6.8, at the same brightness.
- **From the camera's JPEGs** (`core/profile_fit.py`): up to 12 connected RAW files of the camera in the library, each decoded at half size as the sensor has it, against the JPEG inside it (turned to match, the decode's margin cut, both 400 px), the middle 70 % only, flat areas, nothing clipped or black. Fitted in turn: a rising tone curve (medians in bins even in log2, on each pixel's largest and smallest channel, as RGB tone has it), a 3 x 3 matrix that keeps white white (constrained least squares through the curve's inverse), three passes, then a 36 x 8 look table of what is left of hue and saturation (medians, smoothed round the hue circle, held to ±25° and 0.6 to 1.6, grey left alone). Written as "<model> Camera Look.dcp" in `profiles/user` (a new file, never over one), with Adobe's matrix for D65. On the 90D samples, learnt from four and tried on the fifth: 2 to 3.6 levels from the JPEG against 15 to 23 for LibRaw's colours. Refused with a reason: no JPEG inside, too little usable, colours all along one line (greys alone).
- **Colour checker** (`core/colour_checker.py`): Colour Checker... on a photo of an X-Rite ColorChecker Classic: click the middle of dark skin, bluish green, black and white (the four corners as it reads); the 24 squares that will be sampled show over the photo (a perspective from the four), Make Profile. Sampled on the proxy as the edit frames it (turns, crop, lens), medians of a square 0.3 of the patch spacing. The greys set white balance and exposure, then a forward matrix keeping white white, weighted to the dark patches and refined on CIEDE2000, against X-Rite's post-2014 CIELAB (D50). Says its mean and largest ΔE00. "Linear tone" keeps the camera's tones (for reproduction); otherwise Lumina's curve. Named for the light's temperature from the greys; refused when the greys do not get darker from white to black (clicked out of order, not a target).
- **Not yet**: a profile is not part of a preset or copied settings (a profile is of one camera); the white balance does not follow a profile made under another light (a picker would); a hue/saturation map with several value divisions is applied after the exposure, not before as Adobe does; DNG files' own embedded profiles and BaselineExposure are not read; no automatic detection of the target; the fitted look does not know the camera's picture style or Auto Lighting Optimizer setting of each photo (they change the JPEG it learns from).

**Zoom in the Develop view (#33).** Z, a click, Ctrl and the wheel, Ctrl+Plus and Minus and a drag work in the Develop view as in the viewer (`ImageView` is zoomable there; the main window sends the zoom actions to whichever view shows), and what is in view is rendered from the full decode, so sharpening, noise reduction, clarity, texture and grain can be judged at the size they are made for.

- **Region render** (`pipeline.render(..., region=(left, top, right, bottom), haze=...)`, `session.render_region`): the part of the result in view, the same pixels as in the whole render (tests compare them, to a last bit of float rounding, through turns, mirroring, straightening, the crop, every step on, and a render of a smaller copy). Only that part of the geometry is made (the straightening samples just the box). The steps that look at neighbours get the rows and columns they reach around it (`Detail.reach()`), cut at a multiple of `align` as the whole photo is, and the margin is thrown away. The vignette and the grain take a first column as well as a first row. Making that exact meant the smaller copies that clarity, texture and colour noise filter on are now made on whole blocks (`colour.shrunk` and `grown`: the photo is reflected out to a multiple of the factor first), so the copy is the same whichever part is cut from it; before, a width that was not a multiple shifted the copy by up to a pixel across the photo.
- **Dehaze** measures the whole photo, which a part cannot. The measure (air colour and transmission map, on a 512 px copy anyway) is made from the proxy (`pipeline.haze_analysis`, kept in the worker while the edit is the same) and told the size of the whole: close to what the whole render measures from its own pixels (a test bounds the difference), not equal.
- **What is rendered** (`session.render_region(path, look, zoom, centre, view)`): at 100 % or more, the full decode; below, a copy made smaller to the zoom (once per photo and size; the one before goes first), told the full size so sharpening and noise reduction have the radius they would have there. The view's size plus two pixels, around the centre, as fractions of the photo as the edit shows it. Zoomed in past 100 % the pixels are drawn larger by the view, not rendered larger. A 6500 x 4900 photo at 100 % in a 1920 x 1200 view: 0.07 s with the tone controls, 1.1 s with every detail step on (the full decode is 190 MB as 16 bits; nothing larger than the part is held as floats).
- **Showing it** (`ImageView.set_detail`): the part is drawn over the screen-sized image, scaled up, which stays under it and shows where the part is not yet (panning, zooming). It is drawn in its place on whole pixels, so 100 % is sharp. The view asks for a part 80 ms after the zoom or the place stopped changing, and again when a screen-sized render arrives, since that took the old part away.
- **While a control moves**: the proxy, scaled up (the old part is gone as it is of another look), and no part is asked for. The session drops a part that comes back for a look that is no longer the one shown, and a request for a part never takes the place of a waiting one that changes the look (`develop._replaces`). Let go: the screen-sized render, then the part. The status bar says "100 %, rendering…" until it is there.
- **Crop** shows the whole photo: the zoom is put away and zoom is off while it is on, and comes back (as it was) on leaving. Escape: cancels the crop, then back to fitted, then out. Stepping to the next photo keeps the zoom; coming in from the grid starts fitted.
- **Not yet**: a part while a control moves (it would take about as long as a proxy, a part of a view being a megapixel or two, and would show the detail steps live); a margin around the part, so a pan shows no scaled-up edge before the next part comes; the zoom in steps under 100 % renders from a copy that takes about a second to make.

**Opening from the file manager (#43).** `lumina PATH...` takes folders and photos, as paths or `file://` URLs (`app.local_path`); the launcher entry has `Exec=lumina %F` and a `MimeType=` of the types the library reads (a test keeps them in step with `images.PHOTO_EXTENSIONS`).
- **One instance per user** (`integration/single_instance.py`): a local socket named for the user. A second `lumina [PATH...]` hands its paths to the running one as a line of JSON and ends before it opens the database; with no paths the running window comes forward. A socket left by a crash is taken over.
- **A photo of a library folder** opens in the viewer (`Opening.open_photo`); if the folder is being scanned just now, it opens as the grid gets the photo. A folder is added and shown.
- **A photo outside the library: ask once** (decision for #43, options (a) of the issue). It opens in a window of its own (`ui/quick_view.py`, zoomable, nothing kept for it: no flags, rating or edit) with "Add folder to library" and "Not now". The library is not changed unless the user says yes; then the folder is added, scanned, and the photo opens in the viewer. With only such windows open the main window stays hidden.
- **Not yet**: "Show in folder" from the grid (`org.freedesktop.FileManager1`), and the AppImage's own desktop file (#37).

**HDR merge (#27), schema 7.** A bracket of RAW exposures made one photo of linear light that keeps what is past white, which then opens in the Develop view like any other.

- **Derived photos** (`core/db.py`, shared with panoramas, #28; the jobs' common part in `core/derived.py`): `derived` (kind, settings JSON, where the result is: volume and path from its root, as a photo's; NULL until written) and `derived_sources` (in order, by volume, path and content id, not by photo row, so a source whose folder leaves the library or whose file goes missing is still named), and `jobs.derived_id`: the job that makes it. Queuing writes all three in one transaction (`add_derived_job`). Removing a folder keeps the derived rows that were made (they say what a file came from, should the folder come back) and drops those that never will be. `derived_at(volume, path)` tells what a file was made of.
- **Choosing** (`core/hdr.py`): RAW files only (JPEGs would need the camera's response curve recovered), 2 to 9, all of one camera (make and model; refused naming the odd one); all of one size, checked when decoded (failed naming the file). One photo chosen brings its bracket (`brackets`, `bracket_around`): runs of photos at most 2 s apart, of one camera, lens and focal length, at exposures that differ by a third of a stop or more from each other in the run, spread at least 0.9 stops; a burst at one exposure is not one. Several chosen are taken as they are. The frames are put in order of exposure (from shutter, aperture and ISO, darkest first), the middle one the reference.
- **Merging**, in steps the job's thread calls in a worker process of its own (`workers.MERGING`; the job on `workers.MERGE`), so a cancel waits for one step at most:
  1. Decode each frame (`raw_linear`, the full linear decode), all with the reference's white balance (`camera_white_balance`): frames shot on auto white balance would otherwise differ in colour. Each is kept on disk as 16 bits in the job's work folder (`$XDG_CACHE_HOME/lumina/merge/<job>/`), so memory holds one decode at a time and a resumed job skips those done.
  2. Align (`_shift`): median threshold bitmaps from coarse to fine, as OpenCV's AlignMTB, but on both frames scaled to one exposure and clipped alike, the median taken of the pixels clipped in neither and clipped pixels never compared. AlignMTB itself failed on a frame two stops over, mostly white: its median is white and its bitmaps say nothing. Whole pixels, up to 63 either way; 0.45 s at 24 MP.
  3. Plan (`make_plan`): how much brighter each frame is than its neighbour, as the median ratio over the pixels both have well exposed (from 2 to 80 % of white, on a copy of about a megapixel), chained to the reference; the metadata only where too few pixels tell (a camera's 1/60 s is not quite 1/60 s). The result is cut to what every frame covers once shifted.
  4. Merge (`merge_rows`), 128 rows a call: each pixel is the frames' light scaled to the reference's exposure, weighted by the light the frame caught (its ratio: a brighter frame has less noise) times how far its brightest channel is from clipping (all below 80 % of white, none at 95 %). Where every frame is clipped, the darkest one's value. **Deghosting** (off, low, medium, high: a frame may stray 1, 0.6 or 0.35 stops from the guide, then fades out over as much again, the mask blurred over 9 px): the guide is the reference where it is well exposed, else the next darker frame that is; a frame that disagrees there is left out, so something that moved comes from one frame.
- **The file** (`core/linear_tiff.py`): RGB as 16-bit floats (half), uncompressed, in strips, 1.0 at the reference's white, so the light past white is kept (up to 65504 times; 11 bits of precision at every brightness, which 16-bit integers would not give above white). Other editors open it too. The header (with Make, Model, the lens, DateTimeOriginal and SubSecTimeOriginal of the reference, and "HDR merge of N photos") is laid out before any pixel is known, rows go in by offset, in any order. Named after the first photo taken, with "-HDR" (`IMG_0001-HDR.tif`), beside it; written as a hidden `.lumina-merge-<job>.part` there, synced, then put in place by creating the name exclusively, so a file that is there, or appears meanwhile, is never written over: the next name is taken (`-HDR-2`). A cancel or failure removes the part; the originals are only read. When done, the folder is scanned, which brings the photo into the grid.
- **Reading it**: `linear_tiff.is_linear` tells a float TIFF by its header (only `.tif`/`.tiff`). The grid, the viewer and search read it every n-th pixel and show it clipped at white, as an unedited RAW is shown (`images._load_linear`). The edit's decode is the file as float16 (`source.load_linear`, 2 bytes a channel, as a RAW's 16 bits): the pipeline takes any dtype, so exposure below zero and the Basic controls bring back what was past white (on a test merge, the clipped share went from 30 % to 0.6 % at -2 EV). `source.resize` no longer clips floats at white, so the proxy and the screen's copy keep it too.
- **Jobs** (`qt_models/merge.py`, `MergeService`): one merge at a time, in the library's jobs table (kind `hdr`). A quit leaves it queued with its decoded frames; the next start resumes from them. A job whose drive is not connected waits for the drives to change. Cancel in its own status (`job_status.merge_status`, beside the scan's): "Merging IMG_0001-HDR: reading photo 2 of 3", "aligning", "45 %", then "Merged 3 photos into IMG_0001-HDR.tif".
- **UI**: Merge to HDR… (Ctrl+H) in the grid's and the viewer's menus; a dialog lists the photos with their exposures, deghosting and alignment (remembered). A photo in no bracket says so.
- **Memory and disk**: one decode at a time (190 MB at 32 MP), then bands; the work folder holds every frame decoded until the job ends (190 MB each at 32 MP), and is removed then.
- **Not yet**: JPEG brackets; a preview in the dialog; auto-tone of the result (it opens plain, as a RAW does); choosing the reference frame; sub-pixel or rotational alignment; tested on real brackets from a camera (only on generated DNGs so far: `tests/rawfiles.scene` and `bracket_mosaic`).

**Panoramas (#28).** Overlapping photos taken turning the camera, stitched into one photo of linear light, which opens in the Develop view as an HDR merge does. Built on the derived photos above; what both kinds of job share (finding the sources, the work folder, the part file and placing it, the result's tags) is `core/derived.py`, and `MergeService` runs both, one at a time.

- **Choosing** (`core/panorama.py`): 2 to 60 photos chosen in the grid, as they are (no sequence is looked for), of one camera (refused naming the odd one), all RAW or none (refused naming the odd one; a JPEG has no linear white balance to share); all of one size, checked when decoded (failed naming the file). Any photo Lumina reads: RAW, JPEG, HEIC, and linear TIFFs, so HDR merges stitch into an HDR panorama with their light past white. Taken in the order shot; the first one gives its white balance, name and tags.
- **Stitching**, in steps on the merge thread and process as an HDR merge:
  1. Decode each frame in full (RAW files with the first one's white balance), kept in the work folder as it came (16 bits, or half floats for a merge's), with a copy of about 1 MP.
  2. Plan (`make_plan`), on the copies: SIFT features (each copy brought to one median brightness first, or a frame a stop darker finds too few), `BestOf2NearestMatcher`, the biggest connected group (a frame outside it fails naming it), `HomographyBasedEstimator`, `BundleAdjusterRay`, horizontal wave correction. OpenCV's matcher drops a pair whose matches are over about 90 % inliers as the same view; clean frames that overlap well are that too (rotated views of a real CR3 were), so such a pair is kept unless the homography moves no corner more than 3 % of the diagonal: only then is it the same view, refused naming both. **Gains** in linear light: per overlapping pair the median ratio of luminance over the pixels both have well exposed (2 to 80 % of white; no upper limit for a merge), least squares on their logs, geometric mean 1. **Vignetting** is found with them: both frames of a pair see one light, `gain_i L_i / f(r_i) = gain_j L_j / f(r_j)`, with `f = exp(a r² + b r⁴)` (r from the frame's middle, 1 at a corner, one lens for all the frames); each pair's overlap is cut into 8 bins by how much nearer the middle of one frame its pixels are than of the other, a median per bin is an equation, and the gains, a and b are solved together (a ridge of 1 pulls a and b to 0 where the overlaps say little). Only a falloff a lens makes is kept: never brighter out from the middle, a corner not under 10 % of it; else one term, else none. Every frame is divided by `f` in the seams' copies and in the stitch, so dark corners do not band across the seams. **Seams**: OpenCV's graph cut (colour cost) on copies of about 0.1 MP, gamma-encoded after the gains. (The Voronoi seam finder crashes the process in OpenCV 5.0.) **Weights**: each frame's seam mask grown by 1.5 % of a frame's width and feathered over twice that, so frames cross-fade over 3 % across a seam and fade towards their edges. **Crop** (on by default): the largest rectangle all covered, found on the seams' copies (blocks at most 200 000) and kept a pixel of them inside; off keeps everything covered, the rest black. Kept in the work folder: a resumed job does not plan again.
  3. Stitch (`stitch_rows`), 128 rows a call. Not OpenCV's warpers, which warp a whole frame at once and would need the result in memory or on disk to blend into (the plan before starting): for each band, each frame's part of it is projected backwards (cylindrical, spherical or perspective, the same maths as OpenCV's, made here for the band, in strips of at most 8192 columns for `cv2.remap`), only the frame's rows and columns it needs read from the decode on disk, scaled by its gain, weighted by its feathered weight (scaled up from the seams' copy, at least 0.001 where it covers) and, in a frame that clips, less where it is near clipping (as the HDR merge), so an overlap takes lost highlights from a frame that has them. Feathering, not multi-band: multi-band needs the whole result.
- **The file**: a linear TIFF as the HDR merge's, at most 300 MP (made smaller to fit, before the crop), `<first>-pano.tif` beside the first photo, `-pano-2` and on, under the same hidden part and exclusive create. Tags of the first photo, "Panorama of N photos".
- **UI**: Stitch Panorama… (Ctrl+M) in the grid's and the viewer's menus, by Merge to HDR; a dialog lists the photos with the projection (cylindrical by default, spherical, perspective) and the crop (remembered), and a **preview** of the panorama for them (see below). One photo chosen is told to choose more. The merge status says "Stitching IMG_0001-pano: reading photo 2 of 5", "finding how the photos fit", "45 %", "Stitched 5 photos into IMG_0001-pano.tif".
- **Preview** (`core/panorama.py` `preview_*`, `qt_models/panorama_preview.py`): the same plan and stitch on half-size decodes (`decode_frame(preview=True)`: RAW at half size, then about 1 MP, kept as the frame), the result at most 3 MP (`make_plan(max_pixels=)`) and shown at most 1600 px on its longest side, as 8-bit sRGB. `PanoramaPreview` (made by `MergeService.preview_panorama`, None when a drive is not connected) reads the photos once, a step each in the merge process, into a work folder `<work root>/preview/preview-…`, and plans and stitches again for each projection or crop; a result that is not the newest is dropped. The dialog starts it when shown and closes it when done (the folder goes after a step that runs; one a crash left goes after a day). A photo that does not fit is named in the picture's place; Stitch stays possible. Real CR3s (24 MP, five frames): 0.4 s a frame, then 2 s.
- **Speed and memory** (three 24 MP frames, 39 MP result): plan 0.6 to 1 s, stitch 3.5 to 7 s (perspective, 88 MP, 12 s). SIFT on a 1 MP copy holds about 400 MB for a moment (it doubles the copy first); stitching adds 50 to 170 MB. The work folder holds every decode until the job ends, as an HDR merge's.
- **Tests**: views of a made-up cylinder of light (`tests/rawfiles.surroundings`, `view`; `vignetted` for a lens that darkens the corners) as DNGs, matched back to it (normalized correlation over 0.97, brightness within 2 %); the falloff found against the lens's; the preview's shape and scene against the job's, with a fake preview for the dialog; frames a stop apart, HDR merges as frames, every refusal and failure, cancel, resume, the size cap.
- **Tried** on the author's own photos against a Lightroom panorama of the same frames: similar results. Also on turned views of a real CR3 at full size: focal found within 0.02 %, gains exact, no visible seam.
- **Not yet** (#49): 360° panoramas (a frame across the back is planned over the whole width: right but slow) and several rows of frames (should work, untested); a frame made smaller by the size cap is sampled bilinearly, not filtered; no boundary warp or filled edges (out of scope).

**Import from a card (#51), schema 8.** Copying photos from a memory card, or any folder, into a library folder. Until now the library only read photos where they were. Tethered shooting (#57, #58) will reuse the copying.

- **Cards**: a mounted filesystem with a `DCIM` folder at its top (`importing.find_cards`). `ImportService` follows the mounts with the library: a card plugged in says so in the status bar ("Memory card “EOS_DIGITAL” connected: Ctrl+I to import"); nothing opens by itself.
- **Reading** (`importing.read_source`, on a thread, newest read wins): the photos under the card (as a scan finds them: hidden files and what is not a photo, such as videos, left out), each one's size, content id, and the time it was taken. The time is read from the photo's first bytes (`core/capture_time.py`: the EXIF of a JPEG, of a CR3's `CMT2` box, else `CMT1`, and of TIFF-based RAW files), since exiftool reads a CR3 to its end: about 1.2 s a photo from a card in a USB reader (`-fast2` still 0.3 s), so 35 minutes for a card of 1 800, against about 30 s this way, cold. Photos it can't date go to exiftool in batches, and without exiftool the file's time is used; the file times on a card are not the capture time (on the author's 90D card two or three hours off, and seconds later), so they are a last resort. Checked against exiftool on real CR3 and JPEG files (`test_samples`). A photo is **imported before** when its content id is a photo's in the library or an import item's that was copied (`db.imported`), so a photo imported and then removed from its folder is still not offered again. Only reads.
- **Choosing** (`ui/import_dialog.py`, Import Photos…, Ctrl+I, the sidebar's Import… button, and a button on the empty library's page): the card (or Other Folder…), its photos by the day they were taken (newest first, each ticked when it has new photos; a day with none is greyed), "Also photos imported before"; where to (a connected library folder, or any folder, which is then added to the library), the folders (by year and day `2026/2026-10-14`, by year and month `2026/10`, by day, or all in one), the names (as on the card, or the time taken first: `20261014-153012-IMG_0001.CR3`), and a backup copy to a second folder, laid out the same. An example path, the count and size, and the space free there; Import is off without enough space. The choices are remembered.
- **The job** (`importing.run`, kind `import`, on a thread of its own, `workers.IMPORT`): one row per photo in `import_items` (where it comes from, as a volume and path like a photo's, so a card mounted elsewhere next time is found; where it goes; the backup folder; copied, failed or still to copy; where the copy went). It checks the space on every drive it writes to before copying anything, then copies each photo in order: to a hidden `.lumina-import-<job>-<item>.part` beside where it goes, hashed (BLAKE2b) while read from the card, synced, read back from the disk (the page cache dropped first, `posix_fadvise`) and compared, the card's file times kept, then put in place under the first free name by an exclusive create (`derived.place`, now for any suffix): `IMG_0001.CR3`, else `IMG_0001-2.CR3`. A file already there with the same bytes is taken as the copy, so an import run again, or resumed after a crash between putting a copy in place and noting it, never copies twice. A photo that fails (unreadable, read back wrong, no room) is named in the job's failures and the rest go on; the job ends `done` with "Imported 118 photos, 2 could not be copied". Cancel stops between chunks and removes the part; a quit leaves the job queued, and the next start goes on from the next photo not copied. A card or drive not connected leaves it waiting ("Waiting for … to be connected") until the drives change. When it ends its library folder is scanned, which puts the photos in the grid. The status bar: "Importing into Photos: 45 of 120", "Imported 120 photos into Photos".
- Folders merged into a new folder around them keep their merge and import jobs (they used to lose every job; only their scans need to go).
- **Not yet**: thumbnails in the dialog (days only), applying a preset, keywords or a flag on import, ejecting the card when done, videos.

**Import from a camera over USB (#72).** The camera is a source in the Import dialog beside cards and folders, read through libgphoto2 as tethering (#58) is, without the card taken out. Everything of the card import (#51) holds: the days, the layouts and names, the backup copy, read back and compared, never over a file, imported before found by the content id.

- **Found** (`tether.detect`): the USB cameras libgphoto2 knows, listed without opening them, when the dialog is made ("Canon EOS 90D  (camera on USB)"). Not read until chosen: reading holds the camera, and a dialog that opens must not take it from a tether session. The first camera only, as tethering.
- **Listed and read in parts** (`tether.GPhotoCamera.list_files`, `info`, `read_range`; `importing.read_camera`): every file under the camera's storages (two card slots are one source), through PTP, with its size and time there; a photo's date and content id come from its first and last 64 KiB (`range_file.RangeFile`, a file-like object over partial reads that `capture_time.read_file` and `fingerprint.content_id_of` read as they read a file), so nothing is downloaded whole to show the days. The id is the file's: a photo copied from the camera has the id read from the camera. A photo whose start does not give its time has the time the camera gives the file (no exiftool over USB). One that can't be read is named in the reading's failures.
- **Copied** (`importing.copy_from_camera`, shared `_copy_stream`): the same job and items as a card's. A camera item's source is a volume key `camera:<serial>` and the path on the camera. The photo is asked for 4 MiB at a time (cancel between parts), hashed on the way, written to the hidden part, synced, read back and compared; one the camera sends cut short, or that is not the size it was read as, is a failure naming it. The file's time is the camera's, never later than now (its clock may be ahead). A backup copy is made from the copy just checked, not from the camera again: a photo crosses the cable once. Nothing on the camera is written or deleted.
- **Waiting**: no camera, another camera than the one the photos are on, or unplugged in the middle leaves the job queued ("Waiting for the camera to be connected"), the part removed, the photos already copied kept; it goes on from the next photo. Plugging a camera in changes no mount, so the service looks again every 4 s while a job waits for one. A camera another program has says who and how to let it go, as tethering does (`tether.busy_text`).
- **One owner**: a read for the dialog and an import from the camera are not at the same time in Lumina (`ImportService._camera_lock`; an import starting stops a read), and another process (a tether session) has the camera or not as libgphoto2 says.
- **Tests**: `tests/fakes.FakeCamera` reads its card (listing, partial reads logged, failing, cut short, unplugged mid-read); `tests/core/test_importing_camera.py` (parts not whole files, ids equal to the file's, times, failures, only read, layout and names, large photos, backup from the copy, imported before, never over a file, unplugged and resumed, another camera, cancel) and `tests/ui/test_import_camera.py` (the dialog, busy, waiting and retrying, the window).
- **Tried** on the author's EOS 90D (2026-10-17). **Not yet**: a crash in libgphoto2 takes the app with it (the session of tethering is a process of its own; the import's copy is a thread, since the binding lets go of the GIL); several cameras (the first); a camera plugged in while the dialog is open (found when it is made); thumbnails from the camera's own; deleting from the camera after importing.

**Tethered folder (#57).** One library folder whose new photos show as each is written, for any capture program that writes into a folder (`gphoto2 --capture-tethered`, a camera maker's own). The first step towards tethered shooting (#58).

- **Turning it on**: Tether… in a folder's menu in the sidebar asks for a preset for the new photos (none, or one of the presets; remembered) and shows the folder. One folder at a time; Stop Tethering in its menu or Stop in the status bar ("Tethered to Studio: 12 new photos, preset Product"), whose sidebar icon is a camera meanwhile. Not remembered across a quit: a shot written while Lumina was not running is found by the scan at the start, as any photo. It stops by itself, saying why, when the folder is removed, its drive unplugged, or it has too many directories to watch.
- **Finding** (`qt_models/watcher.py`): the watcher watches the tethered folder whatever the watching setting says, and tells of a change there at once (`hot_changed`, with each directory made in it); with watching on, the quiet moment's scan follows as before, so a file that changed after it was read is read again. Stopping goes back to the normal watcher.
- **Taking in** (`core/hot_folder.py`, on a thread of its own, `workers.TETHER`, so a shot never waits behind a scan): one pass at a time takes the changed directories from a queue as they come. Its new files (`library.new_files`: photos directly in the directory, not hidden, that the library has not got as they are) are read once their size and time have held still for 0.5 s (an empty file never), so a file still being written is not read half way. Each is written at once as a scan's walk would (`library.take_in`, no walk; a new one with no edit gets the preset's edit), told to the window, then its content id and metadata are read (`library.read_details`, shared with the scan) with one exiftool kept for the pass. A pass ends 10 s after the last file. A scan that walked meanwhile and found the same file new leaves it (`write_scan` inserts with `ON CONFLICT DO NOTHING`). Search indexing is asked for after each one's details.
- **Showing** (`ui/controllers/tethering.py`): the new photo opens in the viewer, or in the Develop view while that is open, once the grid has it, unless an older photo is being looked at (the one shown is not the last that arrived); stepping onto the newest follows again. A filter or another folder chosen that hides it is said in the status bar.
- **Tests**: a file written in pieces read once, complete; the preset given to new photos only; within seconds with watching off; a folder made while tethered; the viewer and the Develop view following, an older photo kept; stopping (back to the normal watcher), removing the folder and unplugging stop it.

**Tethering a USB camera (#58), what the camera does** (tried 2026-10-17 on the author's EOS 90D, python-gphoto2 2.6.4 with its own libgphoto2 2.5.34, Fedora KDE; nothing written to the card but the test shots).

- Found and opened over USB as it was: neither gvfs nor KDE's KIO had claimed it. Only one process can have the camera: a second gets `-53 Could not claim the USB device`, which the worker must turn into "… is using the camera".
- Settings there: `iso`, `shutterspeed`, `aperture`, `whitebalance`, `imageformat` (RAW, RAW + L, …), `drivemode`, `batterylevel`, `availableshots`, `capturetarget` (Internal RAM or Memory card), `eosremoterelease` (half and full press, for focus first), `eoszoom` and `eoszoomposition` (live view, #59).
- **Where a frame goes**: with `capturetarget` Internal RAM, a frame from the camera's own button comes as `FILE_ADDED //capt0000.cr3` and is never written to the card: computer only, and lost if not fetched. With Memory card, it comes as `/store_00020001/DCIM/100CANON/IMG_6353.CR3` and stays on the card. So "card and computer" is Memory card and should be the default (a frame is never lost); computer only is Internal RAM, with a warning. Set every time the camera is connected; libgphoto2 left it at Internal RAM.
- **Speed**: a 39 MB CR3 from RAM about 1 a second (a burst of 5 at 10 fps came in over 5 s, none lost); from the card 1.6 to 1.7 s each. A remote `capture()` took 4.3 s to return and 6.1 s to the file, blocking the camera's events meanwhile: use `trigger_capture` and take every file from `FILE_ADDED`, so the app's button, the camera's and a burst go the same way.
- **Names and times**: `captNNNN` in RAM starts again every session and the card's `IMG_NNNN` wraps, so the names are Lumina's (the import's naming), from the time in the photo (`DateTimeOriginal` with subseconds, distinct within a burst). The camera's clock was 5 minutes fast, and libgphoto2 sets a saved file's time from it (into the future here).
- Events besides files: `Button 2` (half press), `Button 3`/`4` (full), `CAPTURE_COMPLETE` at the end of a burst; property changes are many and can be ignored.
- **The remote release must let go of both stages**: `Press Full AF` (or `MF`, no autofocus) then `Release Full` leaves the half press held: the 90D's screen goes dark, as with the button half pressed, and it answers every command with `-110 I/O in progress` until turned off and on, or until `Release Half` is sent. Let go of both, it is fine. A camera busy for a moment (writing, a menu or playback open, waking) answers `-110` too: asked again for up to 3 s.
- **Measured with Lumina's session** (cRAW, about 9 MB): from Capture to the frame 2 s with autofocus, 1.5 to 1.8 s without; saved 0.1 s (from memory) to 0.5 s (from the card) later.
- While a program has the camera, its screen shows a computer and the battery: its shutter button works, its menus and playback mostly not.

**Tethering a USB camera (#58), schema 12.** Shooting with the camera connected by USB, each photo into the library as it is taken.

- **Starting** (`ui/camera.py`; Tether Camera… in the sidebar under Import, Ctrl+T): a library folder (connected), the folders laid out as an import's (`2026/2026-10-17`), the session's name (`Tethered 2026-10-17` without one), where the camera keeps the photos (on its card and the computer, the default; or the computer only, faster, with the warning that a photo not yet sent is lost), and a preset; all remembered. Photos go in `<folder>/<layout>/<session>/`. Without python-gphoto2 (the optional `lumina[tether]`) it says how to install it.
- **The session** (`core/tether.py`, `serve`) runs in a process of its own (`workers.start_process`, forkserver, a daemon), spoken to through two queues: commands (stop, capture with or without focusing first, set a setting, fetch again) and what it tells (waiting, busy, connected with the camera and its settings, settings, disconnected, taken, saved, failed, error, ended); a thread of `qt_models/tether.py` hands what it tells to the main thread. A crash in libgphoto2 takes only the process (told as an error, the session ended). At the app's exit it is told to stop and given 3 s.
- **A frame** told of by the camera (its button, Capture, a burst) gets a `tether_items` row before it is fetched. It is written as an import's copy is (a hidden part, synced, read back and compared, put in place by `derived.place`: never over a file, `-2` on a clash, the same bytes already there taken as the copy), named by the time in it and the camera's name (`20261017-110312-IMG_6353.CR3`, the time now when it has none). Only once its row says it is saved is a frame in the camera's memory let go of (`file_delete`); nothing on the card is touched. Fetching that fails is named (Fetch Again in the bar asks again, from the card).
- **Into the library**: the session tethers its library folder (#57) and hands each saved file to it at once (`HotFolder.take`, without waiting for the watcher): the preset, the viewer or Develop view following the newest photo, and search indexing are the hot folder's. Each photo also goes in the session's collection (a manual one of the session's name, made if there is none). Ending the session waits for a frame being fetched, then lets the folder go back to being watched as before.
- **Unplugged and crashes**: a camera unplugged mid-session is told in the bar and waited for; when it is back the session goes on, and its frames still to fetch are fetched again from the card into their own session's folder (`tether_sessions`), or named as lost when they were only in its memory. At the next session after a crash the same.
- **Another program has it** (`-53 Could not claim the USB device`): the processes with the camera's USB device open are found in /proc (`holders`) and told with how to let it go: GVFS ("unmount it in the file manager, or run gio mount -s gphoto2"), KDE (a Dolphin window or the device notifier), or the program's name. Nothing is stopped. Looked for again every second.
- **The bar** (`CameraBar`, above the photos while a session runs): the camera, its battery, shots left and the session's count (or why it can't shoot), the settings as libgphoto2 offers them (ISO, shutter, aperture, white balance, quality, drive; a camera without one leaves it out), Focus first, Capture (Space or F12, so a foot pedal works; only while connected), Fetch Again, End Session. The settings are read again every 15 s and after a change.
- **Tests**: a fake camera kept in a folder (`tests/fakes.FakeCamera`: shots, unplugging, busy, failing fetches, driven from outside the session's process); the frames on the card and in memory, a burst never over a file, names, a copy that reads back wrong, fetching again, unplugged while fetching (fetched when back, or lost from memory), a crash's frame into its own session, waiting, busy with who, settings, capture, stop; the session in a real process; the bar, the dialog and the window. Tried on the author's 90D (above).
- **Not yet**: RAW + JPEG as one photo (they come as two frames, two photos); sessions listed or continued another day (the collection gathers a session's photos); a choice of names (always dated); more than one camera; what a session does when the camera's auto power off turns it off (untried).

**Live view (#59), what the camera does** (tried 2026-10-17 on the author's EOS 90D, as in #58).

- **Frames**: `capture_preview` starts live view by itself (`viewfinder` 1, `output` PC) and gives 960×640 JPEGs of about 200 KB, at about 20 fps when asked for back to back. A picture taken in live view (`eosremoterelease`) arrives 2 s later as usual, and live view goes on.
- **Magnifying needs 1-point AF**: with the AF method on face tracking (`afmethod` `LiveFace`, the author's setting), `eoszoom` is answered with `-110 I/O in progress` for as long as it is asked. With `Live` (1-point) it works. Lumina says to change the AF method instead of changing it.
- **The point**: `eoszoomposition` reads back as `0,0` always, so the camera can't be asked where its point is. It was found by locating magnified frames in the whole one. It is the top left corner, in the sensor's pixels (6960×4640), of a magnifying frame a fifth of the frame across, kept inside the frame. 5× shows that frame, 10× its middle, and the position stays when the magnification changes. Other models' sizes are not known yet, so their point is not moved from Lumina.
- **Autofocus**: `autofocusdrive` 1 returns at once (0.04 s), but works only in live view and only once (see Focus below); the half press is used.
- **Busy**: a setting changed right after live view or magnification can be refused as busy (`-110`) until the camera's events are read.

**Live view (#59).** The connected camera's live view, for framing and focusing in studio work and digitizing.

- **In the session's process** (`core/tether.py`): only one process can have the camera, so live view is the camera session's. While it is on, the session asks for a frame (`capture_preview`, the camera's own JPEG) between looking for events (not waiting for them) and taking commands, and puts it on a queue of its own (`LiveFrame`: its number, the start of live view it belongs to, the JPEG, its `Look`, the zoom and point). **Nothing queues up**: at most two frames are on their way; the next is asked for only once the app says it has the one before (`SHOWN`). Frames the app had no time for are never taken from the camera, and the one shown is always the newest. Each start of live view has a number, and the app drops frames from an earlier start or that arrive after a stop. A stop (`LIVE None`, the session ending) turns the camera's viewfinder off, and no frame is put on the queue after it.
- **A frame's look** (`core/live.py`): a histogram of red, green, blue and luminance, and the share of pixels at 0 and 255 in each colour. It is computed in the session's process from the JPEG decoded at reduced size, so the UI thread never computes it. The clipping overlay (red where a colour is at 255, blue where all three are at 0) is made on the app's frame thread, only while it is turned on.
- **In the app** (`qt_models/tether.py`): a second thread reads the frames, keeps only the newest, decodes it to a QImage and hands it to the main thread. Only one hand-off waits at a time. Live view stops after 60 s with the app in the background and starts again when the app is in front ("Live view stopped while Lumina was in the background"). A camera that sends no frames for 3 s (too hot, a menu open) ends live view with the reason. An unplugged camera's live view starts again when it is back.
- **Zoom and the point**: magnified 5× or 10× (`eoszoom`) around the camera's point (`eoszoomposition`, placed by `canon_position` in the frame of `_POINT_FRAMES`, by model), which on Canon is also where it focuses (`autofocusdrive`). The point is kept in the app as shares of the whole frame. With face tracking AF, magnifying and moving the point are refused with what to change on the camera. A click puts the point there (and focuses there, with Focus on Click, unmagnified). Magnified, a drag or the arrow keys move what is magnified, and a small map at the corner shows where it is.
- **Focus without a picture**: Focus in the camera's bar, beside Capture (`FOCUS`): on Canon a half press of the remote release (`Press Half AF`), let go of after 2 s or before anything else (a capture, another focus, live view started or stopped); in live view at the point. Tried on the 90D: `autofocusdrive` focused only in live view (out of it `-1`) and only once (a second did nothing, even after setting it to 0), while the half press focuses every time, in live view and out of it (each tells `Button 2`), and a capture straight after works. Other cameras: `autofocusdrive`.
- **A capture in live view**: Canon takes the picture in live view, which goes on. A camera that can't stops live view for the picture and starts it again.
- **The page** (`ui/live_view.py`, Live View in the camera's bar): it runs only while the page is shown; Escape goes back to where it was opened. Guides: thirds, a grid, the preset's crop (`crop_guide`: the preset's crop turned and mirrored back onto the camera's frame; straightening ignored), and the session's last photo over the frame at a chosen opacity, for lining up a repeat setup. The histogram sits at the frame's corner, with a corner lit for clipped shadows or highlights, and the clipping overlay. A photo taken in live view does not take the page away: the grid has it.
- **Tests**: the fake camera's live view (frames, failing frames, zoom, the point, focus, a camera that can't capture in live view); at most two unshown frames, and newer ones once shown; a clean stop with no frames after it, in the session and in the app; a new start not held up by an earlier one's frames; failing frames end it with the reason; back after an unplug; paused in the background and on again; the preset's crop on the frame; the page in the window (frames, click to focus, zoom, last shot, a capture keeping the page, Escape, the session ending).
- **Not yet**: the point on Canon models other than the 90D (their frames' sizes); the camera's own overheating warning (only the frames stopping is noticed); a crop guide for a photo turned by the camera's orientation (the frame is as the sensor sees it); live view while the page is not shown; focus peaking.

**Backups of the database (#54).** Every edit, flag, rating and the index are in one SQLite file; `core/backup.py` keeps copies of it.

- **A backup**: SQLite's online backup API, all pages in one step, so one read transaction: a consistent copy while the app goes on writing (in WAL mode a reader holds up no writer). Into a hidden `.library-backup-<pid>.part` in the backups folder, switched out of WAL (one file), `PRAGMA integrity_check`, synced, then put in place by `derived.place` (exclusive create, `-2` on a clash). A failure removes the part; one a crash left is removed by the next backup into that folder. A damaged library can't be backed up (its copy fails the check).
- **Names**: `library-2026-10-16-093012.sqlite3` daily; `…-before-schema-8.sqlite3` before a migration; `…-before-restore.sqlite3`, the library a restore replaced; `…-damaged.sqlite3`, a damaged one a restore moved aside. Only daily ones are rotated; only files named so are ever deleted.
- **When**: at the start and every hour after, on a thread (`workers.BACKUP`), when the newest daily backup in a folder is over a day old; Back Up Now in the settings. Before a migration, always (`db.Library._migrate`, beside the database), with every vector; when it can't be made, the library is not migrated and the app says so (`db.NoBackup`). A new library has none.
- **Where and how many**: `backups/` beside the database, and a second folder the user chose (another drive), each rotated: the newest of each of the last 7 days, then the newest of each of 4 weeks before them (settings). A second folder not there (a drive not connected) is not made, so a backup never lands on the disk under the mount point; the status bar says so.
- **Vectors**: left out of a daily backup when they are more than half the file (deleted from the copy, then `VACUUM`); they are made again by indexing. Rows of photos that could not be read are kept. The settings say when a backup has none.
- **Integrity at start**: `PRAGMA quick_check` before anything opens the database (`application._check_database`). Damaged: the app says what is wrong and offers the newest backup (its date and photo count), or Quit; with no backup, Open Anyway or Quit.
- **Restore** (settings, Backups tab: the backups, newest first, with when, size and kind; the one chosen shows its photos and edits, read on a thread; Restore… asks first): the database can't be swapped while threads have it open, so the app quits (jobs stop and stay queued as on any quit) and starts again in the same process (`os.execv`, `--restore BACKUP`, a hidden argument), which puts it in place before opening anything. `backup.restore`: copies the backup beside the database as a part, checked; backs up the library as it is (or, damaged, moves it and its WAL into the backups folder); checkpoints and leaves WAL mode, refusing if anything still has it open, so no WAL is left to be applied to the file restored; then renames the part over it. A backup of a newer schema is refused; an older one is migrated when opened (with its own pre-migration backup). Any failure leaves the library as it was.
- **Cost** (200 000 photos with vectors, 470 MB, page cache warm): `quick_check` 0.3 s; a daily backup 1.9 s and 51 MB without the vectors; one with them 1.2 s and 470 MB.
- **Not yet**: backing up the thumbnails or the search model (both can be made again); restoring part of a backup (one folder's edits).

**Keywords and collections (#52), schema 9.** Ways to group photos besides folders. Keywords and manual collections are in the database, never in a photo; XMP sidecars (#53, below) carry the keywords, but not collections.

- **Keywords** (`core/keywords.py`, `core/db.py`): a keyword is a path of names from the top, `Places > Finland > Helsinki`, typed with `>` (a `|` too, as XMP's hierarchical subject has it). `keywords` has one row per path, unique without regard to case; the levels above a keyword have rows of their own (so the list is a tree) and are spelt as the keyword already there spells them. `photo_keywords` links a photo to the keywords it was *given*, not to those above them, per photo and not per virtual copy, as flags are. A keyword counts a photo once for itself and each level above; filtering by a keyword shows it and everything below. Rename (moves what is below too; refused onto another keyword's name) and delete (with what is below; the photos stay) are in the sidebar's keyword menu. Both tables go with a photo when its folder is removed from the library; a missing file or drive changes nothing.
- **From the files**: IPTC `Keywords`, XMP `Subject` and `HierarchicalSubject` are read with the details (`Metadata.keywords`) and taken in once per photo (`photos.keywords_read`), so a keyword taken off a photo is not put back when its file is read again. A photo read before this schema is taken in only when its file changes; the files are not read again for it. Never written back.
- **Giving them**: K (and Keywords… in the photo menus) asks for the chosen photos (the grid's, or the one shown): a field with completion over the existing keywords, several separated by commas, and the list of what the photos have ("Dog (1 of 3)" when only some do) with Remove. Changes are made as asked and are one history with flags and ratings (`library_model._undo` holds the keyword ids each photo had), so Ctrl+Z undoes them in order. The viewer's status bar lists a photo's keywords.
- **Showing them**: a sidebar list under the folders with the counts, indented by level; click one to filter, again to stop. A keyword combo in the filters row does the same (the two follow each other). Like the other filters it narrows the rows in the model, so a photo that loses the keyword stays until the user moves on.
- **Collections** (`collections`, `collection_photos`): manual ones hold photos (dropped from the grid onto the sidebar's item, or Add to Collection in the photo menu, Remove from This Collection while one is shown); names are unique without regard to case. A collection is a `db.Filter` (`collection_id`), so it combines with the year, camera and lens filters. Deleting one keeps the photos.
- **Smart collections** (`core/smart.py`): the filters at the time they were saved (year, camera, lens, flag, stars, edit state, keyword and a text search), as versioned JSON in `collections.query`. There is nothing stored of what they hold: choosing one sets the filters again, so it updates itself. Save… beside Clear makes one; "Save Current Filters Here" in its menu replaces what it saved. A text search is only applied when the search model is there.
- **Last Import**: a sidebar item while some import (#51) has copied photos: the photos of the newest import job (`Library.last_import`, `Filter.import_job`, matched to `import_items` by volume and path), nothing stored.
- **Counts** are one query over every link (0.4 s for 100 000 photos with three keywords each, measured; a first version that joined without the range on the path took 20 s), so the service shows the names at once and the counts a moment later from a thread, telling `keywords_changed` again.
- **Not yet**: a keyword's colour or synonyms, collections of virtual copies, nesting of collections, counts that follow the folder chosen.

**XMP sidecars (#53), schema 10.** A `.xmp` beside a photo (`IMG_0001.CR3.xmp`, so a RAW and its JPEG never share one) holding what the database keeps of it, so it travels with the photos and a library can be rebuilt from them. Off at first (settings, Library, Sidecars): nothing is written next to a photo unless asked.

- **The file** (`core/xmp.py`): one `rdf:Description` with the standard `xmp:Rating` and `dc:subject` (every name of every keyword, once, for programs that know no levels) for other tools, and in Lumina's namespace (`lumina:`, version 1) `Updated` (when the library last changed the photo, `time.time()` as text), `Flag`, `Keywords` (a bag of full paths, what is read back) and `Edits` (a sequence of `Copy` and `Params`, the stored parameters JSON as it is, so every copy and a migration later work as for the database). No `crs:` compatibility promise. Only our own part is read back.
- **Safety**: the photo is never touched. Written to a hidden `.lumina-xmp-<pid>-<name>.part`, synced, and put in place: a file of ours (it carries our namespace) is replaced; none there is made by a hard link, which fails when the name is taken, so a file that appears meanwhile is not written over (a filesystem without links, such as a card's exFAT, is checked and renamed instead). Another program's `.xmp` (darktable names its the same) is never read as ours and never written over: it is named as a failure and skipped. A folder that cannot be written to is the same: named, skipped, the rest go on. A file with a document type or entity is refused when read (and one over 8 MB is not ours); one from a newer Lumina is an error naming it.
- **What is out of date** (`photos.changed_at`, `sidecar_at`, `sidecar_mtime_ns`): `changed_at` is set by every change of flag, stars, keywords (also a keyword renamed or deleted) and edits, copies included; `sidecar_at` is the `changed_at` the sidecar holds. A photo is pending while `changed_at` is set and `sidecar_at` is not, or behind it: so a photo never marked has no sidecar, a quit or crash resumes by itself, and turning the setting on writes the whole library with no job of its own. The migration gives what was marked before the time of its edit, else the migration's. Not persisted as a job on purpose: the columns are the queue.
- **Writing** (`core/sidecars.write_pending`, `LibraryService`): one pass at a time on a thread of its own (`workers.SIDECARS`), 3 s after the last change (debounced, so a slider released many times is one write), at the start, when drives change and after a scan; a change during a pass makes another. A photo marked missing, or on a drive not connected, waits. Failures are said in the status bar (the first, and how many more).
- **Reading** (`core/sidecars.read_changed`, the scan's last step, only with the setting on): beside each available photo of the folder, a sidecar whose file time is not the one noted when it was written or read here is read; one newer than the library's own change replaces the photo's flag, stars, keywords and all its edits and copies (`changed_at` takes its time, so nothing is written back); an older one is kept out, and the library's state is written to it. The summary says how many were read in and how many kept out. A gone sidecar is written again; a damaged one is a failure naming it. A sidecar is read once until the file changes, so a flag cleared here is not put back by the same file. A scan costs one more `stat` per photo.
- **Not yet**: reading another program's `xmp:Rating` or `dc:subject`, moving a sidecar with a photo moved by Lumina, collections and smart collections in sidecars (they are the library's, not a photo's), writing on quit (a pending one is written at the next start).

**Finding the actions; scrolling the Develop panel (#77, #76).** There is no menu bar, and most actions are a key or a context menu away.

- **Read from the actions** (`ui/shortcuts.py`): `entries(window)` takes the `QAction`s of the window and of every widget it shows, once each by name (the one with a key), so both lists follow the view that is open and never go stale. An action's group (General, Library, Culling, Viewer, Develop, Stacks and Copies, Merges, Camera) is a property set with `set_group`; a test fails for any action with a key and no group. Keys a widget takes without an action (the backslash held for the original, the live view's arrows) are its `shortcut_hints`.
- **The overlay** (? or F1): the keys of the view open, in groups in columns over the dimmed window, those that can't be used now dimmed. Every key is its own while it shows (no shortcut runs under it); any key or a click closes it, and the focus goes back.
- **The palette** (Ctrl+K, Find an Action): a field over a list of every action but itself, with its key; the names with every word typed, those starting with the first word first. Up, Down and Page keys move, Enter or a click runs it, Escape closes. An action that can't be used now is greyed with why, when known (`shortcuts.enable(action, on, why)`: "No photo chosen", "Choose two or more photos", "No camera connected"…), and does not run; the palette stays.
- **Scrolling the panel**: the wheel used to move every slider it passed over, and each change settled into the edit. Now a slider or a combo box in the panel takes the wheel only with the focus (`controls.wheel_when_focused`, which hands the event to the scroll area itself), and a strip down the panel's right side, away from the photo (`controls.ScrollStrip`, `gap(20)` wide, so it follows the density), has nothing in it to hit, with a faint hint of it under the pointer.

**Robustness pass (#113, on `canary`).** The fixes that followed the code review, in the order they were made; the reasons are in the issues.

- **Migrations (#99).** `executescript` commits what is open and then autocommits each statement, so a migration that failed half way stayed half applied. Migrations now run through `db._script` (statement by statement, in the transaction opened by `BEGIN IMMEDIATE` in `Library._migrate`), with the version bump in the same transaction, and re-read the version under the lock (two connections opening one new file).
- **Unplugged drives (#102).** A photo whose file is gone while its details are read is marked unavailable, and the scan raises `NotConnected` when the folder is gone, so it waits; a rescan reads its details when it is back. An import item whose card was pulled stays to copy (`importing._source_gone`, with the mounts read fresh by the service); a failed backup copy leaves the item copied, and names the backup file in the failures.
- **A file that hangs exiftool (#101).** `library._read_apart`: when a batch times out or exiftool dies and it still answers for a good file (`_works`), the batch is read in halves down to the file, which is named as failed. When it answers for none, the scan stops as before.
- **A worker that dies (#100).** `workers.submit`: the calls in flight in a broken pool are run again one at a time in a new pool, so only the call that kills its worker again fails (`call()` tries twice).
- **Small fixes (#104).** `Library.new_copies` (one transaction); indexing skips by content id (`json_each`), not by `OFFSET`; `add_folder` and `add_job` check inside `BEGIN IMMEDIATE`; a TIFF over 4 GB is refused before the render; a scan removes our own `.lumina-*.part` files older than an hour.
- **Sidecar conflicts (#103).** When the library and the sidecar both changed since they last agreed and the sidecar is newer, the edits it replaces stay as virtual copies after its own; a sidecar whose edit is damaged or from a newer Lumina is refused, named.
- **Large libraries (#111, #105).** Schema 13: `photos_folder_time (folder_id, COALESCE(captured, file_time))`. The year filter and `photos_near` use ranges. A change under a watched folder scans only the changed directories (`scan(only=...)`, `scanner.find_photos_in`; a directory that is gone makes what was below it missing; changes during a scan are scanned when it ends); the full scan stays for the start, a drive arriving and Rescan. `LibraryService.edits_changed` carries the photos whose edit was saved: the model updates their rows in place.
- **Threads (#106).** `remove_folder`, `stack_bursts` and `raw_files_of` run on threads and answer by callback or signal; `unfinished_jobs` is one query.
- **Export as a job (#107), schema 14.** `export_jobs` (options, Replace, folder) and `export_items` (photo, copy, destination, state). `core/exporting.py`: `queue` names the files (`-2` for two of one name, `-edit` for the photo's own name in its own folder), `run` renders each item (in a worker process, from `qt_models/exporting.py`), handles a file that appears meanwhile (the exclusive create of `export.export`), waits for a drive that is not connected, names every failure. The window's "Export Selected…" (grid menu, palette) uses it.
- **Transactions (#108).** `Library.transaction()` replaces `with self.db:` and `_checked_write`: the outermost block takes the write lock and commits, an inner one is a savepoint. `volume_id()` can be called inside a transaction.
- **Writer thread (#106).** `LibraryService._write` queues the window's fire-and-forget writes on one thread with its own connection; `settle()` waits for them before a read, `flush()` also delivers their signals (tests).
- **Split (#108).** `core/db.py` keeps the connection, schema and `transaction()`; the areas are `core/stores/*.py`. `ui/main_window.py` keeps building, folders, the grid and viewer, and editing; tether, search, flags, keywords, collections, copied settings, merging, stacks, virtual copies, import and opening from outside are mixins in `ui/window_*.py`.
- **Records (#108).** `dbtypes.Photo` has every column of `photos` (a test checks it), with `volume_key` and `taken` where they are joined in; `Preset` and `Choices` (a NamedTuple, so unpacking stays). `Library.preset(name)` looks one up.
- **Writes that give something back (#106).** `make_copy`, `paste_settings` (read and written in one transaction), `ensure_keywords`, the keyword and collection edits run on the writer thread and take `on_done` and `on_error`; `flush()` goes on until the writes that callbacks queue are made too. The keywords dialog redraws on `keywords_changed`.
- **The grid without the edits' JSON (#106).** `PhotoRow.edited` is `edits.updated_at`; the thumbnail key is (photo, copy, edited) and the edit is read (without `settle`, as painting must not wait) only when a thumbnail is to be made. `LibraryModel.is_edited(row)` is what the row says; `edit(row)` reads the library.
- **Starting a camera session (#106).** `Library.start_tether_session` writes the session and finds or makes its collection in one transaction, on the writer thread (`LibraryService.start_tether_session`). `CameraService.start` checks the folder and the preset at once and is `running` from then on; the process starts when the session is written. A session ended meanwhile, or written after the app's exit began (`close`), never opens the camera; one that can't be written is told by `error`.
- **Threads, measured (#106).** How long a thread holds up the window, measured with the window's thread doing small units of Python work meanwhile: a scan of 3,000 JPEGs at most 1.5 ms, `similar.find` on 20,000 photos 11 ms (SQLite, hashing and the matrix products let go of the GIL; the Python between them gives it up every 5 ms). They stay on threads. Ranking 200,000 photos held it 26 ms for a text search (median of 15; 43 ms at worst), most of it in `list.sort`, one C call: `Index.rank` now picks and sorts with numpy (stable, so equal cosines keep the grid's order), 8 ms. Ranking every photo for Find Similar is 28 ms, from making the 200,000 pairs the grid takes in.
- **Controllers (#108).** The mixins are gone: `ui/controllers/` has a controller per page (`GridPage`, `ViewerPage`, `DevelopPage`) and per feature (`Browser` for the folders, the sidebar's choice, the filters and the title; `Culling`, `Keywording`, `Collecting`, `Searching`, `VirtualCopies`, `SettingsCopying`, `Stacking`, `Merging`, `Opening`, `Importing`, `Tethering`), and `StatusLine`. Each is given the widgets, actions and services it works with. They share the `Navigator`: which page shows, the photo looked at (`viewed_id`, `viewed_copy`), the photos chosen (`chosen_rows()`), the moves between pages (`show_photo`, `show_develop`, `show_grid`, `step`, `go_back`), and two signals in place of calls across the window: `chosen_changed` (each controller updates its actions) and `status_changed` (the status line). The live view's Escape is the tether's (`Navigator.set_back`). `MainWindow` builds the widgets and the actions, makes the controllers and connects them; the actions call the controllers when triggered, so they can be made first. The photos' menus and the window's own chrome (what the toolbar shows on each page) stay in it.
- **Domain model (#109).** `ui/` imports core's plain-data modules directly instead of the names `qt_models/` re-exported for it: `edit/params.py` (made plain: `LensProfile`, `Perspective`, the curves' identity and `normalize_curve` moved in, `Lens.correction()` became `lenscorrect.correction(lens)`), `dbtypes.py` (with the jobs' kinds and phases, from the modules that run them), `keywords.py`, `smart.py`, `errors.py` (with `NotConnected` and `CameraBusy`) and `edit/export_options.py` (`ExportOptions`, `FORMATS`, `suggested_name`, from `edit/export.py`). `tests/test_layers.py` allows only these from `core/` in `ui/`, and checks that they import only the standard library and each other.
- **One scheduler (#110).** `qt_models/workers.py` replaced its dozen named pools, made from module globals, with lanes declared in one table and one dispatcher: each lane queues its requests by priority (`NOW`, `SOON`, `LATER`) and gives its pool only as many as it has workers, so a request that waits can be cancelled and a viewer's preview goes before thumbnails and exports. The retry of #100 moved into the dispatcher: the requests in flight when a worker dies run again alone, before the rest of the lane. `Token` replaced the `threading.Event`s that stopped work, `Coalescing` the `_again` flags of sidecars and the cache. `qt_models/jobs.py` has the `JobRunner` the scan, index, import, merge and export services now share (start, resume, cancel, wait for a drive, requeue on a quit, run again when asked during a run) and one `JobStatus` instead of five; scans got a thread of their own instead of sharing the window's. A full rescan asked for while that folder is scanned now runs after it instead of being dropped.
- **The Develop view's export as a job (#107).** `DevelopSession.export` queues a job of one file through the ExportService (`exporting.queue_file`, the name the user chose) after the window's writes settle, so the edit exported is the one shown. It shows in the status bar with Cancel and is finished after a restart. The file is rendered in the Develop process by `session.export_open`, from the decode held there, instead of a second full decode in a decode worker; when the photo was closed meanwhile it falls back to one. A file that appears at the last moment is still asked about (`exporting.TAKEN`).

**Jobs outside the window (#86).** A scan, indexing, an import, a merge or an export can run for hours, and the window was the only place that told it.

- **The island** (`integration/island.py`): `IslandClient` is filehouse's client to the Quickshell Island's activities API (`docs/ACTIVITIES_API.md` in the shell's repo) moved from Gio to QtDBus, since Lumina's PyPI PySide6 has no PyGObject beside it: asynchronous calls, the API version checked, a restarted island seen as a new owner of the name. `Activities` is filehouse's reporter without the jobs: told every change, it shows each activity, sends what changed at most four times a second (an end at once), retries what was refused, makes room by dismissing our oldest failure, and puts back what runs when the island restarts. PySide6 cannot send `a(ss)`, so the actions go as variants holding `a{sv}`, which the island's bridge unwraps (tried against `scripts/activities_bridge.py` on a private bus). At the exit, what runs is told it was stopped by the quit and carries on at the next start, waiting for the reply, since the process ends next.
- **What a job looks like there** (`ui/job_reports.py`): the title is what it does ("Scanning Holiday"), the line under it how far ("1 500 of 12 000 · about 25 minutes left"), the end the status bar's words. A job shows after it has run 3 s, so the watcher's quick rescans never do; a failure always does, with what failed by name. Cancel in the island does what the status bar's Cancel does, and the activity runs on until the job reports how it ended. A job that waits for a drive at the start is left to the status bar.
- **Notifications** (`integration/notifications.py`): when a job fails, or one that ran a minute or more ends, while Lumina is not the active app; not when it was cancelled. The first three files that failed are named. `Notify` takes unsigned integers, which PySide6 cannot send, so it is sent with `gdbus call` (GLib's) and its arguments typed in GVariant's text format; a click on it, over QtDBus, brings the window.
- **The time left** moved from the scan into the `JobRunner` (`jobs.Estimate`, with the clock passed in): the phases each service names are timed once they have run 5 s (and, for a scan's details, 100 photos), so imports, exports and indexing tell it in the status bar too.
- **Settings** (General, Desktop): the island and the notifications can each be turned off, on at first. Turning the island off dismisses what Lumina shows there (`Activities.clear`); turned on again, a job that runs on shows at its next progress.
- The taskbar's progress (`com.canonical.Unity.LauncherEntry`) was left out: the shell's dock does not show it.
